### 修复地图 Key 注入缺陷（真机测试暴露）

**问题现象**

真机运行后探索页显示「地图不可用 / 未配置高德地图 Key」，地图不显示。

**根因**

Key 的注入方式选错，属实现缺陷，非配置问题：

- Android 端的 Key 被实现为依赖 `--dart-define-from-file=amap.env` 手动传参。该参数只在显式附加时生效，IDE 运行按钮与不带参数的 `flutter run` 都不会传递，此时 `String.fromEnvironment` 返回空串，`AmapConfig.isConfigured` 为 false，进而命中自定义的「未配置」分支挡掉地图。
- 上一条目的验证只跑了带参数的构建，并据此判定「注入链路贯通」，未覆盖用户实际的启动方式，因此缺陷未被发现。`amap.env` 本身无问题（Key 完整、32 位十六进制、无 CRLF 污染）。
- 经反编译确认，高德原生 SDK 实际从 `AndroidManifest` 的 `com.amap.api.v2.apikey` meta-data 读取 Key（`com/amap/api/col/3sl/ij.class` 中含该字符串并调用 `getApplicationInfo` + `metaData`），Dart 侧的 `MapsInitializer.setApiKey` 只是另一条可选路径。原实现放弃了前者这条在任意启动方式下都生效的通道。

**修复内容**

- `android/app/build.gradle.kts`：构建期读取 `amap.env` 中的 `AMAP_ANDROID_KEY`，经 `manifestPlaceholders["amapApiKey"]` 注入；`AndroidManifest.xml` 增加 `com.amap.api.v2.apikey` meta-data 引用该占位符。Key 仍不入库，manifest 源文件中只有占位符。
- Key 缺失时 Gradle 输出警告；发布构建直接抛 `GradleException` 阻断，不允许静默产出鉴权必然失败的发布包。
- `lib/app/config/amap_config.dart` 重写：`androidKey` / `iosKey` 改为空值时返回 `null` 而非空串。**这修复了第二个隐藏缺陷**——插件的 `checkApiKey` 只判空引用、不判空串，传入 `''` 会调用 `setApiKey('')`，把 manifest 中已注入的有效 Key 覆盖掉。原实现恒定传入空串，即使 manifest 注入正确也会被抹掉。
- `isConfigured` 改为 `isKeyMissing`，且仅对 iOS 生效：Android 的 Key 由构建期保障，运行期无法也无需判断；iOS 无等价 manifest 机制，仍依赖 Dart 注入，故保留运行期判断与说明文案。
- `amap.env.example` 更新为按平台说明注入方式，不再笼统要求附加命令行参数。

**决策说明**

- **优先 manifest 而非要求用户记住参数**：正确的修复不是提示「运行时请加 `--dart-define-from-file`」。任何依赖每次手动传参的方案都会再次退化，且 IDE 运行按钮无法附加参数。manifest 注入在构建期完成，与启动方式无关。
- **Android 运行期不再判断 Key**：Key 在构建期注入，运行期读不到 Dart 侧的值属正常状态。继续判断只会重现误报。
- **发布构建缺 Key 直接失败**：调试构建仅警告以便快速迭代，但发布包缺 Key 必然鉴权失败，属应阻断而非警告的问题。

**验证结果**

- 关键回归验证：执行 `flutter build apk --debug`（**刻意不带** `--dart-define-from-file`，即复现原缺陷的条件），构建成功；`aapt2 dump xmltree --file AndroidManifest.xml` 显示 `com.amap.api.v2.apikey` 的 `android:value` 为真实 Key 值。即原先失败的条件现已注入成功。
- `flutter analyze`：`No issues found!`。
- `flutter test`：16 例全部通过。新增 2 例回归用例：`AmapConfig.isKeyMissing` 在无 dart-define 的环境下为 false（防止「未配置」误报复发）、`androidKey` / `iosKey` 空值时为 `null`（防止空串覆盖 manifest 有效 Key）。原「未配置 Key 时显式说明」用例已按新语义改写为断言不出现「地图不可用」而停在合规告知卡片。
- 密钥未入库：git 将提交的文件中无 Key；Key 字面量仅存在于被忽略的 `amap.env`、`.dart_tool/` 与 `android/.gradle/` 构建缓存中（均经 `git check-ignore` 确认）；manifest 源文件中为 `${amapApiKey}` 占位符。
- **仍未验证**：地图瓦片是否真正渲染、手势实际手感、以及 Key 在高德控制台的鉴权是否通过。本次只证明 Key 已正确进入 manifest；若控制台未登记本机调试 SHA1，运行时仍会鉴权失败并白屏。需重新安装 APK 复测。

**后续计划 / 遗留问题**

| 项目 | 说明 | 状态 |
|------|------|------|
| 重新安装复测地图渲染 | 需装新 APK 确认瓦片显示与手势；若仍失败，下一步查高德控制台 SHA1 登记情况与 logcat 鉴权错误码 | 待验证 |
| 验证方式的教训 | 本缺陷源于「只验证了自己使用的构建命令，未覆盖用户的启动方式」。后续涉及构建期注入的改动，须以最朴素的启动方式验证 | 已记录 |
| iOS 端 Key 注入 | iOS 仍依赖 dart-define，存在同类漏传风险；接入 iOS 时应评估经 `Info.plist` 或原生侧注入 | 计划 |

3. **构建修复**

- `android/build.gradle.kts` 增加子项目 `compileSdk` 提升逻辑：`amap_map` 1.0.15 自身固定 `compileSdk 35`，而其依赖 `flutter_plugin_android_lifecycle` 2.0.35 要求消费方以 API 36+ 编译，否则在 `:amap_map:checkDebugAarMetadata` 失败。

**决策说明**

- **插件选型**：候选中 `amap_flutter_map`（2021-11）、`amap_flutter_location`（2021-11）、`amap_map_fluttify`（2022-12）均声明 Dart SDK `<3.0.0`，在 Dart 3.13.1 下无法解析依赖，实际只有 `amap_map` 可用（声明 `>=3.1.5 <4.0.0`）。该包非高德官方维护、最后发布于 2025-03，属已知风险，记入遗留问题。
- **合规标记不硬编码为 true**：插件的 `hasContains` / `hasShow` / `hasAgree` 三项任一为 false 都会导致地图白屏，但它们表达的是「是否已向用户披露并取得同意」这一事实。直接写死 true 等于在未披露的情况下声称已获同意，因此实现了真实的同意闸门：用户同意前展示告知卡片、不渲染地图，同意后才构建地图组件。当前同意状态为内存态，未持久化，待账户体系落地后迁移到 Supabase。
- **Key 缺失时不渲染空地图**：白屏无法区分「Key 未配置」「鉴权失败」「网络异常」三种原因，故在 `isConfigured` 为 false 时显式说明原因与修复方式。
- **关闭旋转与倾斜手势**：仅开放文档要求的拖拽与缩放。地图保持正北朝上，避免用户误旋转后难以恢复方位，也便于后续路线视图与时间表共用一致的方位参照。
- **Key 的机密性边界**：`--dart-define` 注入的值会进入产物二进制（已实测在 `kernel_blob.bin` 中可检出），故 Key 不具备运行期机密性。其安全性由高德控制台侧的「PackageName + 签名 SHA1」绑定保证，而非靠隐藏 Key 本身。不入库的目的是避免密钥随源码扩散，不是假设它不可提取。
- **compileSdk 覆盖写在 `afterEvaluate` 且置于 `evaluationDependsOn(":app")` 之前**：先尝试 `plugins.withId` 提前配置，但插件脚本随后会把 `compileSdkVersion` 覆写回 35，无效；改用 `afterEvaluate` 后又因模板中既有的 `evaluationDependsOn(":app")` 已强制求值而抛 `Cannot run Project.afterEvaluate(Action) when the project is already evaluated`，故必须置于其前。已在代码注释中记录该顺序约束。
- **仅提升 `compileSdk` 而不动 `targetSdk`**：前者只影响编译期可用 API，后者会改变运行时行为，二者应分开变更。
