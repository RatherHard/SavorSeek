# SavorSeek 项目介绍

## 一句话介绍

**SavorSeek 是一款以真实地图为工作空间、以 Agent 小队协作为智能核心、以用户可控的长期偏好记忆为个性化基础的美食旅行应用，帮助用户完成从美食发现、个性化推荐到路线规划和行程管理的完整决策流程。**

---

## 一、项目背景

随着城市旅行和短途旅行逐渐从“到此一游”转向深度体验，美食已经成为许多人选择目的地、了解地方文化和安排旅行路线的重要内容。

目前，地图应用已经具备较成熟的地点搜索、评分浏览和导航能力；内容平台则积累了大量探店经验、地方攻略和美食推荐。但是，地点信息、用户评价、内容攻略、个人收藏和旅行计划通常分散在不同平台中。用户在陌生城市寻找美食时，往往需要在多个应用之间反复搜索、比较、截图和手动排程。

用户真正需要解决的并不只是“附近有什么餐厅”，而是：

- 哪些地点符合自己的口味和预算；
- 哪些餐厅值得专程前往；
- 如何避开不喜欢的菜系、食材或连锁品牌；
- 如何在有限时间内安排多家美食地点；
- 推荐信息是否可靠，是否存在过期或不确定内容；
- 如果临时更换地点，后续路线如何调整。

传统智能助手大多采用单一文本问答方式，难以充分利用地图的空间关系，也难以让用户了解推荐、核验和规划过程。

SavorSeek 聚焦“美食发现与旅行规划”这一垂直场景，将真实地图、地点数据、用户偏好、旅行计划和 Agent 协作能力结合起来，帮助用户从“想吃什么”进一步完成“去哪里吃、为什么推荐、如何安排路线”的连续决策。

项目核心理念是：

> **地图负责呈现真实空间，Agent 负责理解用户需求，长期记忆负责让推荐越来越贴合用户。**

## 二、解决的问题

### 1. 美食推荐缺乏个性化

传统推荐通常主要参考大众评分、距离和热度，难以综合处理以下需求：

- 偏爱本地小店，不想去连锁品牌；
- 喜欢某种菜系或口味；
- 对某些食材存在忌口；
- 有明确的人均预算；
- 能够接受排队，但不能等待太久；
- 需要在特定时间和区域内安排用餐。

SavorSeek 将用户指令、收藏信息、反馈和旅行上下文转化为结构化偏好信号，提升推荐与个人需求的匹配程度。

### 2. 美食信息分散，用户需要自行判断

餐厅地址、评分、价格、营业状态、菜品特色、探店经验和地方攻略往往来自不同渠道，用户需要自行阅读、筛选和判断。

SavorSeek 通过地点服务和来源管理机制统一组织可用信息，并对来源、更新时间、可信度和不确定性进行提示，帮助用户区分：

- 可验证的地点事实；
- 内容作者或用户的主观体验；
- Agent 根据多项信息形成的推断。

### 3. 地图、推荐与行程之间缺少联动

用户在地图上发现餐厅后，还需要另行安排日期、时间、停留时长、访问顺序和交通方式。地点调整后，后续路线也需要重新安排。

SavorSeek 将地点、推荐和旅行计划关联起来，支持从地图发现地点后直接收藏、加入行程、调整时间和查看路线。

### 4. 美食旅行规划成本较高

美食旅行需要同时考虑地点距离、营业时段、用餐和休息时长、预算、人数、交通方式和行程日期。手动规划容易出现路线过长、时间冲突或预算超限等问题。

SavorSeek 使用结构化行程模型和路线规划能力，帮助用户生成可调整的美食旅行方案。

### 5. 智能结果不透明、用户控制不足

如果系统未经确认就修改用户偏好或旅行计划，容易造成误记忆和意外变更。

SavorSeek 采用“提案—确认—写入”的方式：

- 推荐结果可以选择或拒绝；
- 长期偏好以记忆提案形式提交；
- 路线以行程草案形式生成；
- 高影响操作需要用户确认；
- 行程写入通过版本号和幂等机制保护；
- 用户可以修改、撤销或重新规划。

## 三、核心功能

### 1. 地图美食探索

- 使用高德地图作为真实空间底图；
- 支持美食关键词检索；
- 支持周边地点搜索；
- 支持按照地图范围检索地点；
- 支持价格、评分、菜系、距离等结构化筛选能力；
- 在地图上展示地点 Marker；
- 同时提供地图和列表两种查看方式；
- 支持地点选择、详情查看和结果分页；
- 支持缓存结果、部分结果和失败结果的状态提示。

当前项目已经形成“地点检索—地图标记—地点详情—加入行程”的基础闭环。

### 2. 地点详情与收藏

地点详情可以展示：

- 地点名称；
- 地点类别；
- 地址；
- 经纬度；
- 评分；
- 信息更新时间；
- 来源和坐标系信息。

用户可以：

- 收藏或取消收藏地点；
- 在“我的”页面查看收藏；
- 从收藏列表重新打开地点详情；
- 将地点加入旅行计划。

### 3. 个性化偏好与长期记忆

系统可以记录与美食推荐相关的偏好，包括：

- 喜欢的菜系和口味；
- 偏好的食材；
- 不喜欢或需要避开的食材；
- 可接受的预算；
- 可接受的距离和排队时间；
- 对本地小店、老字号、连锁店和热门店的偏好；
- 收藏、去过、喜欢或不感兴趣的地点。

系统会区分用户明确表达的信息和系统推断的信息。需要长期保存的偏好可以先生成记忆提案，由用户选择接受、编辑或拒绝。

### 4. Agent 队长指令与协作工作室

用户可以以“队长”身份提交任务，例如：

> 帮我找附近适合晚餐的本地小店，人均 150 元以内，不要连锁店。

系统按照不同职责组织 Agent 工作：

- 需求理解；
- 偏好读取；
- 地点检索；
- 事实核验；
- 推荐排序；
- 路线规划；
- 结果汇总。

Agent 工作区可以展示：

- 当前会话状态；
- Agent 角色；
- 任务进度；
- 阶段摘要；
- 推荐结果；
- 路线草案；
- 决策检查点；
- 记忆提案；
- 失败、超时和降级信息。

用户可以取消任务、重试失败任务、选择或拒绝推荐，以及处理记忆提案和路线草案。

### 5. 个性化推荐

当前推荐主要基于结构化规则进行排序，综合考虑：

- 用户提出的地点和区域；
- 菜系和口味要求；
- 预算条件；
- 用户收藏形成的偏好信号；
- 地点评分；
- 地点距离；
- 坐标有效性；
- 地点事实核验结果；
- 忌口或冲突条件。

推荐结果可以携带：

- 排名；
- 匹配摘要；
- 推荐理由；
- 置信度；
- 风险标记；
- 数据更新时间。

### 6. 美食旅行计划管理

- 创建多个旅行计划；
- 按行程日和时段组织地点；
- 记录到店时间和停留时长；
- 支持行程时区和跨时区显示；
- 支持地点加入行程；
- 支持修改日期和时间；
- 支持取消、恢复和删除节点；
- 支持批量操作；
- 支持乐观并发控制和幂等写入；
- 提供路线小地图和全屏路线视图；
- 路线服务不可用时保留地点顺序并明确提示。

### 7. Agent 路线草案

当用户需要规划路线时，Agent 可以根据候选地点生成路线草案，包含：

- 地点顺序；
- 日期；
- 到店时间；
- 停留时长；
- 路线警告；
- 地点快照；
- 目标行程版本。

路线草案需要用户确认后，才能正式应用到旅行计划中。

### 8. 反馈与纠错

用户可以对推荐结果进行：

- 喜欢；
- 不感兴趣；
- 信息不准确；
- 价格错误；
- 营业信息错误；
- 地点不符合需求等反馈。

反馈可以用于修正当前推荐，并在用户允许的情况下影响后续偏好。

## 四、技术方案

### 1. 总体架构

SavorSeek 采用“Flutter 客户端 + Supabase 数据与服务平台 + Edge Functions 领域服务 + 地图服务”的分层架构。

```text
Flutter 移动客户端
        ↓
应用层与领域服务层
        ↓
Supabase Edge Functions
        ↓
Agent 编排、地点检索、路线规划
        ↓
Supabase PostgreSQL / Auth / Realtime / RLS
        ↓
高德地图及其他授权内容服务
```

### 2. Flutter 客户端

Flutter 负责：

- 地图展示；
- 地点搜索和详情；
- 收藏管理；
- Agent 指令栏；
- Agent 工作区；
- 推荐结果展示；
- 旅行计划和时间表；
- 路线小地图；
- 登录与个人设置；
- 加载、空结果、错误和降级状态展示。

客户端通过 Repository、Controller 和依赖注入组织业务能力，降低界面对第三方服务的直接依赖，便于测试、替换和离线降级。

### 3. Supabase 数据与权限

Supabase 主要提供：

- **PostgreSQL**：保存用户、地点、收藏、行程、Agent 任务、推荐、反馈和记忆提案；
- **Auth**：实现用户注册、登录、登出和会话管理；
- **Realtime**：推送 Agent 任务状态和阶段事件；
- **Storage**：为用户图片、笔记附件等内容预留存储能力；
- **RLS**：隔离不同用户的私有数据；
- **RPC**：对收藏、行程、Agent 命令、记忆和路线应用进行受控写入；
- **Edge Functions**：代理外部服务、保护服务端密钥并执行任务编排。

### 4. 地点检索服务

`places-search` Edge Function 负责：

- 校验用户身份；
- 校验关键词、坐标、半径、边界和筛选参数；
- 代理高德 POI 检索；
- 支持文本、周边和地图范围检索；
- 对结果进行字段归一化；
- 处理地点去重；
- 使用服务端缓存；
- 返回部分结果和明确的错误类型；
- 将地点数据受控写入公共地点缓存。

高德 Web Service Key 仅保存在服务端环境变量中，不直接下发到客户端。

### 5. 路线服务

`trip-route` Edge Function 负责代理高德路线服务，当前支持：

- 步行；
- 驾车；
- 骑行。

客户端只提交经过校验的路线节点和出行方式。路线服务不可用时，系统可以降级为地点顺序和直线连接，并向用户明确说明该结果不代表真实路网路线。

### 6. Agent 编排服务

当前 Agent 采用 TypeScript/Deno 实现的规则型多阶段编排，主要流程为：

```text
队长提交指令
        ↓
需求意图解析 + 偏好读取
        ↓
地图地点召回
        ↓
地点事实核验
        ↓
推荐排序
        ↓
可选路线规划
        ↓
生成推荐结果或行程草案
        ↓
用户确认后应用
```

Agent 编排层负责：

- 任务拆分；
- 阶段状态管理；
- 进度事件发布；
- 超时控制；
- 失败重试；
- 降级处理；
- 结构化结果生成；
- 用户取消；
- 推荐选择；
- 记忆提案确认；
- 路线草案应用。

当前版本的 Agent 主要使用确定性规则和结构化数据处理，尚未完成大语言模型及 LangChain 的深度接入。后续可利用大语言模型增强复杂自然语言理解、内容研究和多轮任务规划。

### 7. 数据一致性与安全机制

项目采用以下机制保证数据安全和一致性：

- Auth 与 RLS 隔离用户私有数据；
- 公共地点数据不允许客户端任意写入；
- 高权限操作仅在服务端完成；
- 外部输入进行类型、长度、范围和枚举校验；
- 行程写入使用 `expected_revision` 进行乐观并发控制；
- 使用幂等键避免网络重试导致重复操作；
- 地点引用与地点快照同时保存，保证历史行程可读；
- 记忆和路线修改需要用户确认；
- 外部服务异常时进行超时、重试和降级；
- 推荐展示来源、更新时间、置信度和风险。

### 8. 地图与 Agent 视觉表现

项目规划采用以下分层方式：

- 高德地图负责真实道路、地点和空间关系；
- Flutter 负责地点 Marker、路线节点、详情面板和风险提示；
- 后续可使用 Flame 展示 Agent 像素角色和轻量动效；
- 像素角色只表达 Agent 身份、任务阶段和探索氛围；
- 像素动画不能替代推荐理由、任务状态、距离或路线事实；
- 不对第三方地图底图进行未经授权的截取、重绘或重新分发。

## 五、创新点

### 1. 地图优先的 Agent 交互模式

SavorSeek 不把 Agent 设计成脱离空间环境的普通聊天机器人，而是将地图作为 Agent 的主要工作空间。

用户可以结合当前地图区域、当前位置、选中的地点、行程状态、时间和预算条件向 Agent 小队下达任务，最终结果也会回到地图、地点卡片和行程计划中。

### 2. 从单一助手转向 Agent 小队协作

项目将复杂任务拆分为多个职责明确的 Agent：

- 需求理解；
- 地图探索；
- 偏好读取；
- 事实核验；
- 推荐决策；
- 路线规划；
- 结果汇总。

相比单一黑盒式助手，这种方式更便于观察、调试、重试和局部降级。

### 3. 结构化结果与智能推荐结合

Agent 负责理解需求、组织任务、排序候选和生成解释；地点事实、空间坐标、行程约束和高影响写入则通过结构化数据和确定性规则进行校验。

这种方式可以减少模型自由生成错误地点、错误时间或错误路线事实的风险。

### 4. “提案—确认—写入”的长期记忆机制

系统不把一次推断直接当成用户的永久偏好，而是先形成带有证据和置信度的记忆提案，由用户决定是否接受、编辑或拒绝。

### 5. 路线草案与决策检查点

Agent 生成的路线不会直接覆盖用户原有行程，而是先生成行程草案，并展示计划新增或修改的内容、时间和路线警告、目标行程版本以及可能存在的冲突。用户确认后，系统才通过受控事务应用草案。

### 6. 推荐来源和不确定性表达

项目不仅展示“推荐了什么”，还关注：

- 为什么推荐；
- 使用了哪些信息；
- 信息何时更新；
- 哪些内容属于事实；
- 哪些内容属于主观体验；
- 哪些内容是 Agent 推断；
- 当前存在哪些风险。

### 7. 真实地图与拟人化 Agent 表现分层

真实地图继续承担地点、道路和空间事实，Agent 角色则承担身份、状态和氛围表达。这样既可以增强产品辨识度，又不会让动画取代真实地理信息。

### 8. 面向不稳定外部服务的渐进式降级

地点检索、路线服务和 Agent 编排均设计了异常处理与降级机制：

- 地点服务异常时区分空结果、配置错误、鉴权错误和部分失败；
- 路线服务异常时保留地点顺序；
- Agent 某个阶段失败时，根据任务类型进行重试、降级或终止；
- 刷新失败时尽量保留上一批可用结果。

## 六、应用价值

### 1. 降低美食旅行的信息整理成本

用户可以在一个应用中完成地点搜索、筛选、详情查看、收藏、推荐和行程安排，减少在多个平台之间反复切换和手动整理的成本。

### 2. 提高美食推荐与个人需求的匹配度

系统能够综合用户的口味、预算、忌口、距离、时间和历史偏好，提供比单纯按热度排序更加贴近个人需求的候选。

### 3. 促进地方特色美食发现

项目关注本地小店、老字号、特色街区和地方小吃，帮助用户从热门榜单扩展到更加多样化的地方美食体验。

### 4. 提升美食路线的可执行性

系统将地点、时间、停留时长和路线顺序结合起来，帮助用户形成更加清晰、可调整的美食旅行计划。

### 5. 提升智能推荐的可信度

通过来源、更新时间、置信度、风险提示和用户确认机制，用户可以更好地理解和判断系统建议，而不是无条件接受黑盒结论。

### 6. 探索垂直场景中的 Agent 应用模式

项目以美食旅行这一具体场景为切入点，探索“地图 + 多 Agent + 用户偏好 + 行程规划”的任务协作型 AI 产品形态。

### 7. 具备良好的技术扩展能力

未来可以在现有架构基础上扩展：

- 更多城市和地区；
- 更多授权内容来源；
- 更复杂的推荐模型；
- 更精细的路线规划；
- 语音或多模态输入；
- 多人协同行程；
- 更丰富的反馈学习能力；
- Flame 像素化 Agent 角色。

## 七、使用说明

### 1. 环境准备

开发和演示建议准备：

- Flutter SDK；
- Supabase CLI；
- Docker Desktop；
- Node.js LTS；
- Deno；
- Android Studio、Android SDK 或 iOS 开发环境；
- Android 模拟器或真实设备；
- 有效的 Supabase 配置；
- 有效的高德地图 Key 和 Web Service Key。

### 2. 获取并启动项目

```bash
git clone <repository-url>
cd SavorSeek

cd apps/mobile
flutter pub get
flutter run
```

常用检查命令：

```bash
flutter analyze
flutter test
dart format .
```

### 3. 启动本地 Supabase

```bash
supabase start
supabase db reset
```

启动 Edge Functions：

```bash
supabase functions serve places-search
supabase functions serve trip-route
supabase functions serve agent
```

### 4. 基本使用流程

1. **进入应用**：打开 SavorSeek，进入“探索”“行程”或“我的”页面。
2. **完成地图合规确认**：首次使用地图时，阅读并同意地图服务相关隐私与合规说明。
3. **登录账号**：在“我的”页面完成邮箱注册或登录。收藏、行程和 Agent 服务需要有效登录状态。
4. **探索美食地点**：在探索页输入关键词，例如“海鲜”“大连本地菜”“附近烧烤”等。
5. **查看地图和列表结果**：搜索结果会同时显示在结果列表和地图标记中。没有有效坐标的地点仍可能显示在列表中，但不能用于地图路线。
6. **查看地点详情**：点击地图 Marker 或地点列表项，查看名称、类别、地址、评分、来源和更新时间等信息。
7. **收藏地点**：在地点详情中收藏感兴趣的地点，之后可以在“我的”页面查看收藏列表。
8. **创建旅行计划**：进入“行程”页面创建一个或多个美食旅行计划，并设置标题、日期、时区、人数和预算等信息。
9. **加入行程**：从地点详情中选择“加入行程”，选择目标行程、日期、到店时间和停留时长。
10. **管理行程节点**：在行程页面查看时间表和路线小地图，并根据需要改期、取消、恢复或删除节点。
11. **提交 Agent 指令**：在 Agent 指令栏输入任务，例如“帮我找人均 150 元以内的本地特色晚餐，不要连锁店”。
12. **查看 Agent 工作区**：查看 Agent 小队的角色、执行状态、阶段摘要、推荐结果、路线草案和风险提示。
13. **确认或修改结果**：用户可以选择或拒绝推荐，对记忆提案进行接受、编辑或拒绝，并在确认路线草案后将其应用到行程。
14. **提交反馈**：对推荐结果进行喜欢、不感兴趣或信息不准确等反馈。

### 5. 异常处理

遇到以下情况时，可以根据界面提示处理：

- **定位超时**：使用默认区域或手动搜索；
- **网络异常**：重试请求，必要时使用缓存结果；
- **地图 Key 未配置或鉴权失败**：检查本地配置和高德控制台绑定信息；
- **Agent 超时**：重试或取消当前任务；
- **路线服务不可用**：使用地点顺序和直线连接的降级结果；
- **行程版本冲突**：刷新行程后重新提交操作；
- **部分地点检索失败**：查看当前仍然可用的部分结果。

### 6. 当前功能边界

当前项目重点聚焦：

- 美食地点探索；
- 个性化规则推荐；
- 地点收藏；
- 美食行程管理；
- Agent 任务编排；
- 路线展示。

当前暂不承诺：

- 餐厅在线订座；
- 在线支付和订单履约；
- 专业级实时导航；
- 完整社交社区；
- 未经授权抓取内容平台数据；
- 医疗或营养诊断；
- 多人实时共同编辑行程；
- 完整 Flame 像素角色系统；
- 已接入大语言模型的生产级 Agent 服务。
