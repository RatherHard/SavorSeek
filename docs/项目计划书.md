# SavorSeek 项目计划书

## 一、项目概述

本项目计划开发一款以地图交互为核心、以智能 Agent 为主要能力的美食旅行应用。应用面向把美食探索作为旅行重要目的的人群，帮助用户发现值得前往的餐厅、小店、街区和地方特色美食，并根据用户的口味偏好、旅行时间、预算、交通方式以及实时信息，生成个性化的美食推荐与旅行路线。

与传统地图应用主要提供地点检索、导航和评价浏览不同，本项目希望把分散在地图、用户笔记、内容平台和历史交互中的信息组织起来，通过多个具有明确职责的 Agent 协同分析，让用户能够以更加自然、直观和有趣的方式完成“想吃什么、去哪里吃、怎么安排一天”的决策。

项目的核心理念是：**地图负责呈现真实空间，Agent 负责理解用户需求，长期记忆负责让推荐越来越贴合用户。**

## 二、背景与痛点

目前市面上的地图 App 已经具备较强的美食地点检索、筛选和导航能力，但对于将美食视为旅行主要目的之一的人群而言，仍存在以下问题：

1. **个性化程度不足**
   - 推荐通常依赖大众评分、距离和热度，难以准确区分用户的具体偏好。
   - 对“喜欢清淡但能接受一点辣”“偏爱本地小店、不喜欢连锁店”“愿意排队但不超过一小时”等细分需求支持不足。
   - 用户在不同时间、不同城市中的偏好变化无法得到持续记录和利用。

2. **信息来源较为单一**
   - 地图上的商户信息、评分和评论具有一定结构化优势，但往往无法完整呈现餐厅特色、隐藏菜单、最佳到店时间和真实体验。
   - 小红书、B 站等内容平台中存在大量美食探店、地方攻略和路线经验，但这些信息分散、非结构化，用户需要自行搜索、阅读和整理。
   - 内容平台信息可能存在时效性、商业推广和重复搬运等问题，单纯聚合并不能直接转化为可靠建议。

3. **现有地图 Agent 交互较为单薄**
   - 许多应用中的智能助手主要以文本问答为主，无法充分利用地图上的空间关系和地点信息。
   - 用户难以直观看到 Agent 为什么推荐某家店、如何比较多个地点，以及推荐结果如何影响路线安排。
   - 单一 Agent 往往需要同时处理搜索、筛选、事实核验、推荐和路线规划等不同任务，结果解释性和可控性有限。

4. **美食旅行规划成本较高**
   - 用户通常需要在多个平台之间反复切换，分别查找餐厅、景点、交通、营业时间和排队情况。
   - 美食地点之间的距离、用餐时段、路线顺序和预算约束难以同时考虑。
   - 收藏的店铺、看过的视频和过去的用餐记录没有形成可复用的旅行资产。

因此，本项目立足于 Agent 技术和地图交互，希望整合多来源信息与用户长期偏好，为喜欢前往各地探索当地美食的用户提供一个易用、有趣、可解释且具有持续学习能力的应用。

## 三、项目目标

### 3.1 总体目标

实现一个以地图上的交互为主体的美食旅行 Agent 应用，使用户能够通过自然语言、地图操作和可视化 Agent 协作，完成从美食发现到旅行规划的完整流程。

### 3.2 具体目标

1. 在地图上展示美食地点的空间分布，支持地点查看、搜索、筛选、收藏和对比。
2. 分析用户的搜索、点击、收藏、评价和行程记录，并以长期记忆的形式保存用户的口味与美食偏好。
3. 在符合平台规则和授权范围的前提下，接入小红书、B 站等内容来源，扩充美食信息、探店经验和地方攻略。
4. 建立可视化的多 Agent 工作室，让用户能够看到不同 Agent 的职责、任务状态、分析依据和协作结果。
5. 让 Agent 综合利用地图信息、用户记忆和外部内容，完成美食推荐、地点筛选、宝藏小店探索和美食路径规划等任务。
6. 在地图基础上生成由 Agent 管理和维护的美食旅行规划表，支持按天、按时段查看和调整。
7. 对推荐结果提供清晰的理由、信息来源和不确定性提示，增强用户对结果的理解与信任。

## 四、目标用户与典型场景

### 4.1 目标用户

- 将地方美食作为旅行重要目的的旅行者。
- 喜欢探索本地小店、老字号和非热门餐厅的美食爱好者。
- 希望减少搜索和规划成本，但仍然希望保留自主选择权的用户。
- 需要在有限时间内安排多家餐厅、特色小吃和相关活动的短途旅行者。
- 对内容平台探店信息感兴趣，但没有时间自行整理的用户。

### 4.2 典型使用场景

**场景一：城市初次探索**

用户到达一个陌生城市后，在地图上查看附近具有地方特色的美食。用户可以告诉 Agent“我今天住在这里，想吃本地菜，预算每人 150 元，不想去连锁店”，系统结合地图和用户偏好给出候选地点，并解释推荐理由。

**场景二：宝藏小店发现**

用户希望避开热门景区附近的同质化餐厅，寻找本地人常去的小店。探索 Agent 根据区域、菜系、内容平台提及情况、评价文本和距离进行综合筛选，展示若干候选，并标记营业时间、排队风险和信息可信度。

**场景三：一日美食路线规划**

用户提出“从上午十点到晚上八点安排一条美食路线，中间要留出休息和交通时间”。规划 Agent 综合营业时段、地点距离、用餐时长和预算生成路线，用户可在地图上拖动、替换或删除地点，系统自动更新计划。

**场景四：根据个人口味持续推荐**

用户多次收藏川菜、潮汕牛肉和街边小吃，并经常避开甜味较重的食物。系统在后续推荐时逐渐提高相关结果的排序，同时允许用户查看、修改和清除已记录的偏好。

## 五、项目范围

### 5.1 项目包含范围

项目实现的是面向美食旅行的地图 Agent 应用，不是泛用性的地图应用，应始终专注于美食发现、信息整理、推荐和旅行规划相关功能。

首期范围包括：

- 地图展示与美食地点检索。
- 用户偏好与长期记忆管理。
- 多来源美食信息的统一整理。
- 多 Agent 协同推荐与路径规划。
- 美食旅行计划表的生成、编辑和保存。
- 推荐依据、来源和风险提示。
- 用户反馈收集与推荐结果优化。

### 5.2 暂不包含范围

为控制首期项目复杂度，以下能力暂不作为 MVP 的必要功能：

- 餐厅在线支付、订座和订单履约。
- 泛化到景点、酒店、购物等全部旅行领域。
- 对所有内容平台进行无授权的自动化抓取。
- 完全替代专业地图导航和实时交通服务。
- 复杂的社交社区、直播和商业化广告系统。
- 对用户健康状况进行医疗或营养诊断。

## 六、核心功能设计

### 6.1 地图与地点探索

- 在地图上以标记、聚合点或区域热度展示美食地点。
- 支持按菜系、价格区间、距离、评分、营业状态、特色标签和用户偏好进行筛选。
- 点击地点后展示基础信息、特色菜品、用户评价摘要、内容平台提及、营业时间和位置关系。
- 支持收藏、标记“已去过”、加入旅行计划和地点对比。
- 支持从地图框选区域，并让 Agent 针对选定区域进行探索。
- 对地点信息标注更新时间，降低因商户变更造成的误导风险。

### 6.2 用户画像与长期记忆

系统记录与推荐相关的用户信息，包括：

- 偏爱的菜系、口味、食材和用餐类型。
- 可接受的价格范围、距离和排队时长。
- 对连锁店、热门店、街边摊、老字号等类型的偏好。
- 已收藏、已去过、明确喜欢或不喜欢的地点。
- 在不同城市、不同旅行场景下的临时偏好。

长期记忆需要遵循“用户可见、用户可控、最小化保存”的原则。用户应能够查看系统记住了什么、纠正错误记忆、删除单条记忆或清空全部偏好。对推断得到的偏好，需要明确标记为“系统推测”，不能将推测当作用户明确表达的事实。

### 6.3 多来源信息整合

在平台许可、接口授权和相关法律法规允许的前提下，系统可以利用公开或授权的数据来源：

- 地图和商户基础信息。
- 用户公开评价和结构化评分。
- 小红书、B 站等平台中的公开探店内容或授权接口数据。
- 用户主动提交的笔记、照片和体验反馈。

系统对外部内容执行去重、摘要、时间识别和来源标注，并尽可能区分：

- 可验证的事实信息，例如地址、营业时间和菜品名称。
- 内容创作者的主观体验，例如“适合拍照”“排队较久”。
- Agent 基于多项信息得到的推断，例如“更适合午餐而非晚餐”。

对于可能过期、存在推广倾向或缺乏交叉验证的信息，界面应提供相应提示，不将内容平台的观点直接呈现为确定事实。

### 6.4 多 Agent 协作工作室

建议将 Agent 按职责拆分，形成可观察、可解释的协作流程：

1. **需求理解 Agent**：提取用户的地点、时间、人数、预算、菜系、忌口和其他约束。
2. **地图探索 Agent**：根据地理范围和地点数据召回候选餐厅与美食点。
3. **内容研究 Agent**：整理授权内容来源中的探店信息、特色描述和用户经验。
4. **偏好记忆 Agent**：读取相关用户记忆，并在用户同意或符合设置的情况下更新偏好。
5. **事实核验 Agent**：检查营业时间、地址、重复信息和明显冲突，标记不确定内容。
6. **推荐决策 Agent**：综合用户需求、偏好、地点特征和信息可信度进行排序。
7. **路线规划 Agent**：结合营业时间、地点距离、停留时长和交通约束生成可执行路线。
8. **结果汇总 Agent**：将各 Agent 的产出整理为用户可以理解和操作的推荐或计划。

用户不一定需要看到全部内部推理过程，但应能看到每个 Agent 的任务状态、关键输入、输出摘要、来源和最终影响。系统应展示可解释的结论，而不是暴露不必要的内部思维链。

### 6.5 美食旅行规划表

- 支持按日期、上午/午餐/下午茶/晚餐等时段组织地点。
- 记录地点、预计到达时间、停留时长、预算和备注。
- 在地图上同步显示计划中的地点和路线顺序。
- 当用户替换地点、调整时间或删除节点时，自动重新计算后续安排。
- 对营业时间冲突、路线过长、预算超限和排队风险进行提示。
- 支持保存多个草稿，并允许用户手动锁定不希望被 Agent 自动修改的节点。
- 支持导出为适合查看的行程清单，具体分享能力可在后续版本扩展。

### 6.6 反馈与纠错

- 用户可以对推荐结果进行“喜欢”“不感兴趣”“不准确”等反馈。
- 用户可以指出营业时间、菜品、价格或地点信息错误。
- Agent 在推荐后主动询问必要的反馈，但避免频繁打扰用户。
- 反馈用于改进当前行程和未来推荐，并明确告知用户是否会影响长期记忆。

## 七、产品交互与体验设计

### 7.1 交互原则

1. **地图优先**：地图是主要工作区，文本对话和 Agent 面板服务于地图决策，而不是取代地图。
2. **结果可操作**：推荐结果应能直接收藏、加入计划、替换路线节点或查看来源。
3. **过程可观察**：用户能够了解系统正在搜索、核验、比较还是规划，减少等待时的不确定感。
4. **结论可解释**：推荐应说明与用户需求和偏好之间的匹配关系。
5. **用户可接管**：任何自动生成的路线和偏好都应允许用户修改、拒绝和撤销。
6. **信息有边界**：对过期风险、数据缺失和内容冲突进行诚实提示，不夸大 Agent 的能力。

### 7.2 主要页面

- **首页/地图页**：展示当前位置、搜索入口、地图标记、推荐区域和快捷筛选。
- **地点详情页**：展示餐厅信息、特色摘要、来源、评价、用户笔记和操作按钮。
- **Agent 工作室页**：展示 Agent 列表、任务状态、协作关系和阶段性结果。
- **旅行计划页**：以时间表和地图路线两种形式展示美食行程。
- **个人偏好页**：展示系统记忆、偏好编辑、隐私设置和数据删除入口。
- **收藏与历史页**：管理收藏地点、去过的地点、用户反馈和历史计划。

### 7.3 可访问性与容错

- 地图标记不能作为唯一的信息传递方式，应提供列表或卡片视图。
- 关键按钮、状态和错误提示应支持清晰的文本表达与键盘/辅助技术访问。
- 对定位失败、网络异常、外部数据不可用和 Agent 超时提供明确的降级方案。
- 在低网速或移动设备环境下优先展示缓存的基础地点信息。
- 为复杂动画和 Agent 状态变化提供减少动态效果的设置。

## 八、系统架构与核心技术路线

### 8.1 技术选型

- **客户端**：Flutter
  - 使用跨平台 UI 能力，支持移动端快速迭代。
  - 负责地图展示、交互操作、对话界面、Agent 工作室和旅行计划管理。
- **后端/BaaS**：Supabase
  - 使用 PostgreSQL 保存用户、地点、收藏、记忆、内容和行程数据。
  - 使用 Auth 实现用户身份认证。
  - 使用 Storage 保存用户上传的图片和笔记附件。
  - 使用 Realtime 向客户端推送 Agent 任务状态或行程更新。
  - 使用 Row Level Security（RLS）隔离用户私有数据。
- **Agent 框架**：LangChain（TypeScript）
  - 编排多 Agent 任务流程。
  - 管理工具调用、结构化输出、上下文和记忆检索。
  - 对接地图、数据库、内容检索和路线规划等工具。
- **地图服务**：根据目标地区和授权情况选择合适的地图及地理编码服务。
- **内容检索**：对授权内容建立结构化索引，可结合关键词检索与向量检索。

### 8.2 分层架构

1. **表现层**：Flutter 页面、地图组件、对话组件、计划表和状态展示。
2. **应用层**：用户需求解析、推荐请求、行程编排、反馈提交和权限校验。
3. **Agent 编排层**：负责 Agent 调度、工具调用、任务状态、超时、重试和结果汇总。
4. **领域服务层**：地点检索、偏好记忆、内容摘要、事实核验、推荐排序和路线规划。
5. **数据层**：Supabase 数据库、向量索引、对象存储和缓存。
6. **外部服务层**：地图服务、内容平台授权接口、地理编码服务和其他必要 API。

### 8.3 关键数据实体

- `users`：用户基本信息与账户配置。
- `places`：餐厅、美食点和地点基础信息。
- `place_sources`：地点信息来源、更新时间和可信度。
- `reviews`：评价及其摘要、标签和情感信息。
- `content_items`：外部内容的标题、链接、摘要、来源和时间。
- `user_memories`：用户偏好、记忆类型、来源、置信度和更新时间。
- `favorites`：用户收藏与备注。
- `trips`：美食旅行计划。
- `trip_items`：计划中的地点、时段、顺序和锁定状态。
- `agent_tasks`：Agent 任务、状态、输入摘要、输出摘要和错误信息。
- `feedback`：用户对地点、推荐和行程的反馈。

## 九、MVP 版本规划

### 9.1 MVP 必须实现的能力

1. 用户登录和基础个人设置。
2. 地图展示及地点搜索。
3. 地点详情、收藏和基础筛选。
4. 通过对话输入美食需求，并生成结构化需求条件。
5. 基于地图数据和用户偏好的推荐结果。
6. 基础用户偏好记录、查看和删除。
7. 生成一日美食路线和时间表。
8. 展示 Agent 任务状态和推荐理由。
9. 对地图数据和外部内容进行来源、更新时间和不确定性标注。

### 9.2 MVP 可暂缓的能力

- 多平台内容的全面自动同步。
- 复杂的实时排队预测。
- 多人共同编辑旅行计划。
- 社区动态、关注、点赞和评论体系。
- 自动订座、支付和商户运营后台。
- 高度拟人化的 Agent 角色和复杂 3D 场景。

## 十、实施阶段与里程碑

### 阶段一：需求分析与原型设计

- 明确目标用户、核心场景和 MVP 边界。
- 完成用户流程、信息架构和低保真交互原型。
- 确定地图服务、数据来源和内容使用权限。
- 输出数据库初版设计和 Agent 职责划分。

**阶段成果**：产品需求文档、交互原型、技术方案和数据字典。

### 阶段二：基础能力搭建

- 初始化 Flutter 项目和 Supabase 项目。
- 完成用户认证、基础数据库表和 RLS 策略。
- 接入地图、地理编码和地点详情能力。
- 完成地图页、地点详情页和收藏功能。

**阶段成果**：可以浏览和管理美食地点的基础版本。

### 阶段三：Agent 与记忆能力开发

- 实现用户自然语言需求解析。
- 实现地点检索、偏好读取、推荐排序和结果汇总流程。
- 建立用户偏好记忆的新增、更新、查看和删除机制。
- 加入超时、重试、错误提示和基础日志。

**阶段成果**：可以根据用户需求生成个性化美食推荐。

### 阶段四：路线规划与可视化工作室

- 完成多地点路线规划和时间表生成。
- 实现地图与行程计划的双向联动。
- 展示多 Agent 的任务状态、结果摘要和来源信息。
- 支持用户调整路线并让 Agent 重新规划。

**阶段成果**：可以完成一日美食旅行规划的可用 MVP。

### 阶段五：内容来源与质量优化

- 接入经过授权的内容来源或建立可替换的数据适配层。
- 增加内容去重、摘要、更新时间和可信度处理。
- 根据用户反馈优化推荐排序和记忆准确性。
- 完成性能、可访问性、安全性和异常场景测试。

**阶段成果**：形成可进行用户试用和演示的稳定版本。

## 十一、质量与验收指标

### 11.1 功能指标

- 用户可以完成从搜索地点到加入旅行计划的完整流程。
- 推荐结果能够正确遵循预算、时间、区域和菜系等硬性约束。
- 用户可以查看、修改和删除系统保存的偏好记忆。
- 路线调整后，地图和时间表能够保持一致。
- 外部信息具备来源和更新时间标识。

### 11.2 体验指标

- 首次用户能够在较少步骤内完成一次基础美食规划。
- Agent 任务状态清晰，长耗时任务不会让用户误以为应用失去响应。
- 推荐结果具备可理解的理由，用户可以快速判断是否适合自己。
- 在常见网络异常和数据缺失情况下，应用能够给出可操作的降级结果。

### 11.3 技术指标

- 核心业务逻辑具备单元测试和集成测试，目标测试覆盖率不低于 80%。
- 重点用户流程通过端到端测试，包括地图浏览、推荐、收藏和行程生成。
- 私有用户数据通过 RLS 和服务端权限校验隔离。
- 对 Agent 调用设置超时、重试次数和成本控制上限。
- 对关键数据变更、外部请求失败和 Agent 错误保留可检索日志。

## 十二、数据安全与合规要求

1. 不在客户端代码、代码仓库或日志中硬编码 API Key、数据库密钥和其他敏感凭据。
2. 用户偏好、历史记录和旅行计划属于用户私有数据，必须进行身份认证和行级权限控制。
3. 只收集实现推荐和规划所必需的数据，提供明确的隐私说明和删除机制。
4. 外部内容的获取、存储、摘要和展示必须符合平台规则、接口协议和相关法律法规。
5. 对外部链接、用户输入和 Agent 工具参数进行校验，避免注入、越权和不安全请求。
6. 对用户上传的图片和文本进行类型、大小和内容校验，避免恶意文件或异常输入影响系统。
7. 对推荐结果进行事实与时效性提示，不对营业状态、价格和排队情况作无依据的绝对承诺。
8. Agent 的工具权限遵循最小权限原则，涉及写入用户记忆、修改行程等操作时保留用户确认或撤销能力。

## 十四、结语

美食旅行不仅是寻找“评分最高的餐厅”，更是一个结合个人口味、地方文化、时间安排和空间探索的综合决策过程。本项目希望通过地图、内容和 Agent 的结合，把复杂且分散的美食信息转化为用户真正能够理解和执行的建议。

项目首期将坚持小范围、强场景和可验证的原则，优先完成美食地点探索、个性化推荐和一日路线规划三项核心能力。在此基础上，通过可靠的数据来源、透明的推荐依据和可控的长期记忆，逐步构建一个真正懂用户、能协助规划、同时保留用户自主权的美食旅行助手。
