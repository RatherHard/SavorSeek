> **文档用途**：本文件是后续编码 Agent 的执行依据，不是功能设计稿。Agent 应按“前置决策 → 数据层 → Flutter 数据与状态 → 探索页 → 我的页 → 集成验证”的依赖顺序实施，并在每个阶段完成验证后再进入下一阶段。
>
> **依据**：`docs/探索页美食地点与收藏功能设计.md`、当前仓库代码和测试基线。
>
> **当前状态**：仅完成规划，尚未开始本功能代码实现。

## 1. 执行规则

### 1.1 目标

在不破坏当前“关键词检索 → 地图标记 → 地点详情 → 加入行程”链路的前提下，补齐以下闭环：

```text
关键词检索
  → 地图 + 地点列表
  → 选择同一地点
  → 地点详情
  → 收藏 / 取消收藏
  → 我的页查看收藏
  → 取消收藏后跨页面同步
```

### 1.2 必须遵守

1. **先读后改**：修改文件前读取当前版本；不要假设设计文档中的“已设计”已经实现。
2. **先测试后实现**：新行为先补测试并确认测试能捕捉缺失行为，再写最小实现。
3. **保持现有架构**：继续使用构造函数注入、`ChangeNotifier`、sealed 状态和手写 Fake；本阶段不引入 Riverpod、Bloc 或新的全局状态框架。
4. **不覆盖无关改动**：当前工作区已有行程时间选择相关未提交改动，收藏功能不得修改、回滚、格式化这些无关文件。
5. **公共地点与用户关系分离**：不得把 `isFavorite` 添加到 `Place`，不得把收藏写入 `places`。
6. **UI 不直连 Supabase**：Widget 只能接收状态和回调；Supabase RPC 调用只能位于 Repository。
7. **不虚构事实**：当前数据不足时不得显示评分、价格、营业状态、菜品、图片、推荐理由或内容摘要。
8. **收藏与行程解耦**：收藏、取消收藏不得改变行程；加入行程不得自动收藏；不得接入长期记忆写入。
9. **错误不泄露内部细节**：用户界面和客户端日志不得出现 JWT、API Key、Service Role Key、SQL、堆栈、RPC 内部名称或完整上游响应。
10. **每阶段留下证据**：记录实际运行的命令、通过/失败结果、未完成验证和阻塞项；不要把“迁移文件已创建”写成“线上数据库已更新”。

## 3. 前置决策门

这些事项来自设计文档第 14 节。没有决策时，Agent 不得自行通过代码猜测。若没有产品/架构负责人另行批准，按“建议默认”推进，但必须在实施记录中注明采用了默认值。

| 编号 | 事项 | 建议默认 | 影响 |
|---|---|---|---|
| D-01 | 地点删除后的收藏关系 | `favorites.place_id` 使用 `ON DELETE CASCADE`；行程仍依靠 `place_snapshot` 保留历史可读性 | 数据迁移、收藏列表空缺行为 |
| D-02 | 收藏写入方式 | 统一使用 `security definer` RPC；基础表不开放客户端写入 | RPC、授权、错误映射 |
| D-03 | 收藏读取方式 | 探索页按当前结果查询收藏状态；我的页使用分页收藏列表；避免无界拉取全部收藏 | Repository 接口和性能 |
| D-04 | 收藏备注 | 数据库预留 `note varchar(500)`，MVP 不开放 UI | 表结构，不扩展 UI |
| D-05 | 未登录检索 | **保持当前实现：检索仍要求登录**，不在本阶段放宽 Edge Function 权限 | 未登录状态、登录引导测试 |
| D-06 | 未登录收藏 | 显示收藏按钮，点击打开已有登录/注册 Sheet；登录成功后不自动替用户收藏 | 详情、卡片、可访问性 |
| D-07 | 结果列表形态 | 地图内底部结果抽屉/受控结果面板；不得遮挡固定 Agent 指令栏 | 探索页布局、手势 |
| D-08 | 结果排序 | 保留地点 Repository 返回顺序；不按收藏状态重排 | 搜索结果一致性 |
| D-09 | 埋点 | MVP 不新增埋点系统；不得为埋点阻塞收藏闭环 | 范围控制 |
| D-10 | 长期记忆 | 收藏不自动写入长期记忆；后续单独设计用户可见提案与确认流程 | 隐私、Agent 边界 |
| D-11 | 扩展地点信息 | 暂不加入评分、价格、营业状态、菜品、内容摘要、推荐理由 | 数据契约、来源与时效 |

### 3.1 必须先处理的设计矛盾

设计文档一处描述未登录用户可以浏览公开地点，另一处和当前实现均要求检索认证。MVP 默认不改现有认证策略：

- 未登录可以看到探索页底图和页面结构；
- 未登录不能调用当前 `places-search` 检索服务；
- 未登录点击收藏进入登录引导；
- 若以后要开放匿名缓存浏览，必须另开任务，重新设计 Edge Function 鉴权、缓存数据暴露范围、限流和测试，不能在本任务中顺手放宽。

## 4. 目标架构与数据流

### 4.1 分层

```text
Presentation Widget
    ↓ 状态 / 回调
Page Controller / Application State
    ↓ 抽象接口
Repository
    ↓ Supabase RPC / Edge Function
Supabase 表、RLS、数据库函数
```

本阶段不要求一次性搬迁现有目录到 `domain/data/presentation`，优先在现有 `features/places/` 平铺结构内完成垂直切片，避免无关重构。

### 4.2 单一事实源

| 事实 | 事实源 |
|---|---|
| 公共地点名称、类别、地址、坐标、更新时间 | `Place` / `places` |
| 当前检索结果、分页和选中地点 ID | `PlaceSearchController` |
| 当前用户收藏 ID、单地点写入状态、收藏列表 | 共享 `FavoriteController` |
| 地图标记、地点卡片、详情 | 上述状态的 UI 投影，不保存独立事实 |
| 行程中的历史地点内容 | `trip_items.place_snapshot`，不受收藏变化影响 |

### 4.3 推荐结构

```text
AppShell
├── FavoriteController（只创建一个）
├── ExplorePage
│   ├── PlaceSearchController
│   ├── AmapSurface
│   ├── PlaceResultsSheet
│   ├── PlaceCard
│   └── PlaceDetailSheet
└── MinePage
    ├── 收藏列表
    └── PlaceDetailSheet
```

`ExplorePage` 和 `MinePage` 接收同一个 `FavoriteController`。不得让两个页面分别创建自己的收藏状态。

## Phase 1：Supabase 收藏数据层

### 任务 P1-1：新增收藏表和索引

**新增文件**：

- `supabase/migrations/20260827000013_favorites_schema.sql`

> 若该迁移序号已被其他分支占用，使用下一个未占用序号，并在实施记录中更新实际文件名。

**实现**：

```sql
public.favorites
├── id uuid primary key default gen_random_uuid()
├── user_id uuid not null references auth.users(id) on delete cascade
├── place_id uuid not null references public.places(id) on delete cascade
├── note varchar(500)
├── created_at timestamptz not null default now()
└── updated_at timestamptz not null default now()
```

必须包含：

- `unique (user_id, place_id)`；
- `(user_id, created_at desc)` 索引；
- `note` 为空或去除首尾空格后长度 1–500 的约束（MVP 不开放输入）；
- 更新时间 Trigger（沿用仓库现有数据库风格）；
- `favorites` 启用 RLS；
- 认证用户只能读取自己的行；
- 若采用 RPC 写入，撤销 `anon` / `authenticated` 的表写入权限；
- 不创建任何公共读取全部用户收藏的策略。

### 任务 P1-2：新增幂等记录与 RPC

**新增文件**：

- `supabase/migrations/20260827000014_favorites_rpcs.sql`

**实现要求**：

1. 新增专用 `favorite_idempotency_keys`，不要复用行程专用 `trip_idempotency_keys`，避免语义和清理策略混淆。
2. 幂等记录至少包含：`user_id`、操作名、幂等键、请求哈希、结果、创建时间。
3. 唯一键至少覆盖 `(user_id, operation, idempotency_key)`。
4. 所有 RPC 使用 `auth.uid()`，不得接受客户端传入 `user_id`。
5. `add_favorite`：地点必须存在；重复请求返回幂等成功；并发下最终只有一条收藏。
6. `remove_favorite`：重复取消按幂等成功处理，不把“本来就不存在”当作内部故障。
7. 同一幂等键复用但请求参数不同必须拒绝。
8. `list_favorites` 限制 `limit` 和 `offset`，例如 `limit` 允许 1–100、`offset >= 0`。
9. RPC 使用固定安全 `search_path`，撤销不必要的公开执行权限，仅授予 `authenticated` 执行必要函数。
10. 返回地点名称、类别、地址、坐标、坐标系、`fetched_at`、provider 等最小字段，不返回 `raw`。

**建议稳定错误码**：

```text
unauthenticated
invalid_request
place_not_found
permission_denied
idempotency_conflict
service_unavailable
```

### 任务 P1-3：数据库验证

**新增文件**：

- `supabase/snippets/verify_favorites.sql`

该文件只能作为人工/环境验证脚本，不能替代自动化测试，也不得写入真实用户凭据。

**至少验证**：

- 用户 A 只能读 A 的收藏；

- `search_path` 已固定；

## Phase 3：FavoriteController 与会话安全

### 任务 P3-1：实现收藏状态 Controller

**新增文件**：

- `apps/mobile/lib/features/places/favorite_controller.dart`

沿用 `ChangeNotifier`，Controller 至少维护：

- 当前用户 ID；
- 当前收藏地点 ID 的只读集合；
- 每地点独立的 pending 状态；
- 每地点最近一次可重试失败；
- 收藏列表状态（idle/loading/loaded/empty/failed）；
- 未完成操作的幂等键、前置状态和操作序号。

**收藏操作状态机**：

```text
notFavorite
  → saving
  → favorite

notFavorite
  → saving
  → 失败：回滚 notFavorite + 可重试错误

favorite
  → removing
  → notFavorite

favorite
  → removing
  → 失败：回滚 favorite + 可重试错误
```

**必须满足**：

1. 乐观更新，点击后立即反映目标状态。
2. 同一地点 pending 时忽略重复点击；A pending 不阻塞 B。
3. 失败回滚到该操作前的真实状态。
4. 重试同一次未确定请求时复用原幂等键。
5. 新业务动作使用新幂等键。
6. 使用地点级操作序号，旧响应不能覆盖新状态。
7. 用户登出、切换账号或会话失效时清除旧用户状态；旧请求返回不得重新写回旧状态。
8. `dispose` 后不得通知监听者。
9. 对外暴露不可变集合。
10. 认证成功后加载收藏状态，但不自动执行用户刚才在未登录状态点击过的收藏动作。

### 任务 P3-2：接入 AuthService

**依赖**：`apps/mobile/lib/features/auth/auth_service.dart`

监听 `userIdChanges`：

```text
用户 A 登录 → 清空旧状态 → 加载 A
登出       → 立即清空状态和收藏列表
用户 B 登录 → 不复用 A → 加载 B
```

若加载失败，不要把失败伪装成空收藏；UI 应能区分“没有收藏”和“收藏服务失败”。

| 地点不存在 | “这个地点已无法收藏，可能已被下架。” | 不提供无意义重试 |
| 服务不可用 | “收藏服务暂时不可用，请稍后重试。” | 重试 |
| 未配置 | “收藏服务尚未就绪。” | 提示配置，不伪装为空 |
| 权限错误 | “当前账号无法修改这条收藏。” | 记录并按产品策略处理 |

禁止把以下内容直接给用户：

- PostgreSQL 错误码；
- SQL/RPC 名称；
- `FunctionException` 详情；
- 请求 URL；
- 高德 Key、Supabase Key、Service Role Key、JWT；
- 完整原始响应和堆栈。

## 8. 安全与隐私边界

1. `favorites.user_id` 始终由数据库 `auth.uid()` 决定。
2. 客户端不得传 `p_user_id` 作为权限依据。
3. 公共地点和用户收藏分表。
4. 高德 Web Service Key 仅存在 Edge Function 环境变量。
5. 收藏备注虽然暂不开放，也必须在数据库层限制长度；未来 UI 开放时还需输入校验。
6. 地点名称和地址按普通文本渲染，不把外部内容作为 HTML。
7. 外部来源链接未来若开放，必须校验协议和主机白名单。
8. 日志不得记录完整 JWT、用户邮箱、收藏备注或完整第三方响应。
9. 收藏不自动写长期记忆；不把收藏直接解释成“喜欢”。
10. 当前 HTTP Supabase 地址只能用于开发验证；公开发布前必须完成 HTTPS，并移除不必要的明文传输例外。
11. 地图版权、隐私同意和必要归属不得被结果抽屉、详情 Sheet 或其他覆盖层遮挡。

## 10. 推荐执行顺序与并行边界

### 严格顺序

```text
P0-2 RPC 契约冻结
  → P1 数据库迁移/RLS/RPC
  → P2 Flutter Repository
  → P3 FavoriteController
  → P4 地点列表与统一选择
  → P5 详情和探索页接入
  → P6 我的页与跨页面同步
  → P7 集成、RLS、真机验证
```

### 可并行

P1 完成 RPC 契约冻结后，可以并行：

- 数据库 Agent：P1-1、P1-2、P1-3；
- Flutter 数据 Agent：P2-1、P2-2、P2-3；
- UI Agent：P4-1、P4-2、P4-3，使用 Fake 状态。

但以下依赖不能跳过：

- P2 的 Supabase Repository 不能早于 RPC 返回契约冻结；
- P3 的真实状态测试不能早于 Repository 接口确定；
- P5 不能绕过 Controller 直接把 Supabase 接入详情；
- P6 必须在共享 Controller 创建后再做跨页面同步；
- P7 的真实收藏 E2E 必须在目标数据库迁移和权限核验后运行。
