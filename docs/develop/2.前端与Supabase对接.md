## 关键契约：读写路径不对称

这是实现时最容易出错的地方。参见 `supabase/migrations/20260821000002_itinerary_schema.sql:310-311`：

```sql
revoke all on public.trips, public.trip_days, public.trip_items,
  public.trip_idempotency_keys from anon, authenticated;
grant select on public.trips, public.trip_days, public.trip_items to authenticated;
```

- **读**：`authenticated` 仅有 `select` 权限，用 `.from('trips').select(...)`
- **写**：表的 insert/update/delete 权限已全部 revoke，**必须走 RPC**（`security definer` 函数）

直接 `.from('trips').insert(...)` 一定失败。写入用 `.rpc()` 调用 `create_trip` / `add_trip_day` / `add_trip_item`。

RLS 策略（同文件 303-308 行）限定 `user_id = auth.uid()`，因此**没有认证会话时读取必然为空**，不是 bug。

## RPC 签名

摘自 `supabase/migrations/20260821000003_itinerary_rpcs.sql`，全部返回 `jsonb`：

```
create_trip(
  p_idempotency_key uuid, p_title varchar(80),
  p_timezone text = 'Asia/Shanghai',
  p_start_date date = null, p_end_date date = null,
  p_party_size smallint = 1, p_currency_code char(3) = 'CNY',
  p_budget_limit_minor bigint = null, p_budget_scope text = null,
  p_default_travel_mode text = 'walking')

add_trip_day(
  p_trip_id uuid, p_expected_revision bigint, p_idempotency_key uuid,
  p_local_date date, p_available_start_time time = null,
  p_available_end_time time = null, p_budget_limit_minor bigint = null,
  p_notes varchar(1000) = null)

add_trip_item(
  p_trip_id uuid, p_expected_revision bigint, p_idempotency_key uuid,
  p_trip_day_id uuid, p_item_type text, p_place_id uuid,
  p_title varchar(120), p_planned_start_at timestamptz,
  p_planned_end_at timestamptz, p_time_slot text = 'flexible',
  p_position integer = 0, p_estimated_cost_min_minor bigint = null,
  p_estimated_cost_max_minor bigint = null, p_notes varchar(1000) = null,
  p_place_snapshot jsonb = null)
```

两个必须遵守的调用约定：

1. **幂等键**：每次写入生成一个 uuid 作为 `p_idempotency_key`。重试必须复用同一个键，否则会重复创建。结果缓存在 `trip_idempotency_keys`。
2. **乐观并发**：`add_trip_day` / `add_trip_item` 需传 `p_expected_revision`，取自 `trips.revision`。版本不匹配时 RPC 拒绝写入，客户端应重新读取后重试。

## 字段映射

现有 UI 模型（`trip_models.dart`）与数据库表字段不是一一对应，需要转换层：

| UI 模型 | 数据库来源 | 说明 |
|---------|-----------|------|
| `TripPlan.id` | `trips.id` | uuid |
| `TripPlan.title` | `trips.title` | |
| `TripPlan.destination` | **无对应列** | 需自行取舍：新增列或由行程项推导 |
| `TripPlan.updatedAt` | `trips.updated_at` | |
| `TripDay.date` | `trip_days.local_date` | |
| `TripDay.label` | **无对应列** | 客户端格式化生成（如「周六 · 8 月 22 日」） |
| `TripStop.title` | `trip_items.title` | |
| `TripStop.subtitle` | **无对应列** | 由 `time_slot` + 起止时间拼装 |
| `TripStop.startAt` / `endAt` | `planned_start_at` / `planned_end_at` | timestamptz，注意时区 |
| `TripStop.type` | `trip_items.time_slot` | **枚举不一致，见下** |
| `TripStop.note` | `trip_items.notes` | |
| `TripStop.isLocked` | `is_place_locked` / `is_time_locked` / `is_order_locked` | UI 是单个 bool，库里是三个，需决定合并规则 |

枚举差异需要显式映射：

- UI `TripStopType`：`breakfast, lunch, dinner, snack, activity, rest`
- 库 `time_slot`：`breakfast, morning, lunch, afternoon_tea, dinner, late_night, flexible`
- 库另有 `item_type`：`place_visit, break`

`snack` 对应 `afternoon_tea`，`rest` 可能对应 `item_type = 'break'`，`morning`/`late_night`/`flexible` 在 UI 侧无对应值。**映射规则需先确认再编码**，不要随意猜测。

## 实施步骤

建议按此顺序，每步可独立验证。

### 第 1 步：初始化客户端

`apps/mobile/lib/main.dart` 当前仅 7 行，直接 `runApp`。需改为 async 并在 `runApp` 前初始化：

```dart
await Supabase.initialize(
  url: SupabaseConfig.url,
  anonKey: SupabaseConfig.anonKey,
);
```

`SupabaseConfig`（`lib/app/config/supabase_config.dart`）已备好 `url` / `anonKey` / `isConfigured`，通过 `String.fromEnvironment` 读取，无需改动。未配置时应给出可见提示而非静默失败。

### 第 2 步：认证会话

没有会话则 RLS 下读取恒为空，此步不可跳过。最小实现可用邮箱注册/登录（服务端 `GOTRUE_MAILER_AUTOCONFIRM=true`，无需邮箱验证即可登录）。

需处理会话持久化与过期刷新（`supabase_flutter` 默认已含本地持久化）。

### 第 3 步：实现只读查询

替换 `SupabaseTripRepository.loadPlan()` 的抛异常逻辑。建议单次嵌套查询避免 N+1：

```dart
.from('trips')
.select('*, trip_days(*, trip_items(*))')
.order('local_date', referencedTable: 'trip_days')
.order('position', referencedTable: 'trip_items')
```

保留现有 `TripRepositoryException` 与 `TripRepositoryErrorKind`（`unavailable / unauthenticated / network / conflict`），把 PostgREST 错误映射到对应 kind，UI 已有分支处理。

`InMemoryTripRepository` 和 `DemoTripRepository` 应保留，用于测试与无网络演示。

### 第 4 步：写入 RPC

按上文签名封装 `create_trip` / `add_trip_day` / `add_trip_item`，实现幂等键生成与 revision 冲突重试。

### 第 5 步：注入配置

```
--dart-define=SUPABASE_URL=http://192.144.135.246:8000
--dart-define=SUPABASE_ANON_KEY=<anon key>
```

anon key 存于服务器 `/opt/savorseek/.env` 的 `ANON_KEY`（该 key 设计上可公开，随客户端分发）。**切勿使用 `SERVICE_ROLE_KEY`**，它绕过全部 RLS。

项目已有 `--dart-define-from-file` 惯例（参见 `amap.env`），建议沿用同一方式管理，注意 `.gitignore` 已忽略 `*.env`。

## 明文 HTTP 的影响

当前 `SUPABASE_URL` 只能用 `http://`，服务端尚未配置 HTTPS。这带来两个必须处理的问题：

1. **平台限制**：Android 需在 manifest 声明 `android:usesCleartextTraffic="true"`，iOS 需配置 ATS 例外。否则请求会被系统直接拦截，且报错信息容易被误判为服务端故障。
2. **安全风险**：anon key、用户密码、JWT 全部明文传输，可被中间人截获。

建议在正式联调前先为服务端配置域名 + HTTPS，可省掉上述平台配置，也消除凭据泄露风险。若暂时保持 HTTP，应仅限开发环境。

## 验证方式

服务端可用性已确认，因此联调失败时应优先怀疑客户端。可用以下命令确认服务端仍正常（`<ANON>` 取自服务器 `.env`）：

```bash
# 应返回 200
curl -s -o /dev/null -w "%{http_code}\n" \
  -H "apikey: <ANON>" http://192.144.135.246:8000/rest/v1/

# 注册并取得 JWT
curl -s -X POST -H "apikey: <ANON>" -H "Content-Type: application/json" \
  -d '{"email":"dev@example.com","password":"<password>"}' \
  http://192.144.135.246:8000/auth/v1/signup

# 用上一步的 access_token 查询，应返回 []
curl -s -H "apikey: <ANON>" -H "Authorization: Bearer <JWT>" \
  "http://192.144.135.246:8000/rest/v1/trips?select=id"
```

客户端侧建议补充的测试：

- Repository 单元测试：用 mock 覆盖成功、未认证、网络错误、revision 冲突四种路径
- 字段映射转换的单元测试，尤其枚举映射与时区处理
- 端到端：注册 → 创建行程 → 添加日期与行程项 → 读回校验
