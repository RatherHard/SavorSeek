# SavorSeek 产品需求文档（PRD）

## 一、文档说明

### 1.1 文档目的

本文档把 [`docs/项目计划书.md`](../项目计划书.md) 中的产品构想拆解为可实现、可验证、可排期的需求条目，作为 SavorSeek MVP 阶段设计、开发、测试和验收的唯一需求基线。

本文档只描述**产品要达到什么效果**，不规定具体实现方案。数据库表结构、Agent 编排细节和接口契约由 `docs/architecture/` 下的架构文档承接（该目录为计划产出，当前尚未创建）。

### 1.4 需求编号规则

功能需求使用 `FR-<模块段><序号>` 编号，非功能需求使用 `NFR-<序号>`。编号一经发布不再复用，废弃需求保留编号并标记状态为“已废弃”。

| 编号段 | 模块 | Scope（提交规范） |
|--------|------|-------------------|
| FR-1xx | 账户与个人设置 | `mobile` / `supabase` |
| FR-2xx | 地图与地点探索 | `map` |
| FR-3xx | 用户画像与长期记忆 | `memory` |
| FR-4xx | 多来源信息整合 | `content` |
| FR-5xx | Agent 编排与工作室 | `agent` |
| FR-6xx | 推荐与解释 | `recommendation` |
| FR-7xx | 美食旅行规划表 | `trip` |
| FR-8xx | 反馈与纠错 | `recommendation` / `memory` |

### 1.5 优先级定义

| 优先级 | 含义 | 处理方式 |
|--------|------|----------|
| P0 | MVP 必须实现，缺失则 MVP 不成立 | 必须进入 MVP 验收清单 |
| P1 | MVP 期望实现，可在能力受限时降级 | 允许以简化形态交付，需记录降级说明 |
| P2 | MVP 之后实现 | 仅保留需求描述，不占用 MVP 排期 |

## 二、产品定位

### 2.1 一句话定位

SavorSeek 是一款以地图为主工作区的美食旅行助手：用户在地图上表达和调整需求，多个职责明确的 Agent 负责理解、检索、核验和规划，长期记忆负责让推荐随使用逐步贴合用户口味。

### 2.2 与既有产品的差异

| 维度 | 通用地图 App | 内容平台 | SavorSeek |
|------|--------------|----------|-----------|
| 推荐依据 | 评分、距离、热度 | 创作者主观体验 | 用户长期偏好 + 地点数据 + 授权内容 + 硬性约束 |
| 结果形态 | 地点列表 | 图文视频 | 可解释推荐 + 可执行行程 |
| 过程透明度 | 不展示 | 不适用 | 展示 Agent 任务状态、依据与来源 |
| 偏好可控性 | 弱 | 无 | 记忆可见、可改、可删 |

### 2.3 产品原则

产品原则继承项目计划书第 7.1 节，并作为需求取舍时的判据：

1. **地图优先**：对话与 Agent 面板服务于地图决策，不取代地图。
2. **结果可操作**：任何推荐结果都能直接收藏、加入计划或替换节点。
3. **过程可观察**：长耗时任务必须暴露阶段状态。
4. **结论可解释**：推荐必须说明与用户需求、偏好的匹配关系。
5. **用户可接管**：自动生成的偏好和行程均可修改、拒绝、撤销。
6. **信息有边界**：对过期风险、数据缺失、来源冲突做诚实提示。

发生冲突时，**信息有边界 > 用户可接管 > 结论可解释 > 结果可操作 > 过程可观察 > 地图优先**。即：宁可少给一条结论，也不给一条无来源、无时效标注的结论。

## 三、目标用户

### 3.1 用户画像

**画像 A：主题式美食旅行者（主要目标用户）**

| 项目 | 描述 |
|------|------|
| 特征 | 每年 2 至 6 次短途旅行，选目的地时美食权重高于景点 |
| 目标 | 在有限天数内吃到有地方代表性、非旅游化的餐食 |
| 痛点 | 需要在地图、点评、内容平台之间反复切换整理信息 |
| 关键需求 | FR-2xx 地点探索、FR-6xx 可解释推荐、FR-7xx 一日路线 |
| 成功标志 | 一次会话内得到可直接执行的当日美食安排 |

**画像 B：本地小店探索者**

| 项目 | 描述 |
|------|------|
| 特征 | 常驻或长期停留某城市，主动避开热门商圈 |
| 目标 | 找到本地人常去、评价样本少但口碑稳定的小店 |
| 痛点 | 热度排序把小店压在长尾，且信息时效性差 |
| 关键需求 | FR-2xx 区域框选探索、FR-4xx 来源标注、FR-3xx 偏好积累 |
| 成功标志 | 推荐结果中出现自己未知且事后认可的小店 |

**画像 C：口味约束明确的用户**

| 项目 | 描述 |
|------|------|
| 特征 | 存在明确忌口、辣度上限、预算上限或排队容忍上限 |
| 目标 | 推荐结果不违反硬性约束，无需逐条人工筛除 |
| 痛点 | 现有筛选项覆盖不到细分口味描述 |
| 关键需求 | FR-5xx 需求结构化、FR-3xx 记忆管理、FR-6xx 约束校验 |
| 成功标志 | 硬性约束零违反，且系统正确记住长期约束 |

### 3.2 非目标用户

以下人群不作为 MVP 设计对象，其需求不构成需求取舍依据：

- 商户经营者与运营人员（无商户后台）。
- 只需导航与实时路况的用户（不替代专业导航）。
- 需要订座、支付、外卖履约的用户。
- 需要营养或医疗建议的用户（明确不提供）。

| 偏好记忆的记录、查看、修改、删除 | FR-301 ~ FR-308 |
| 地点信息的来源、更新时间与不确定性标注 | FR-401 ~ FR-404 |
| 自然语言需求解析与 Agent 任务状态展示 | FR-501 ~ FR-510 |
| 可解释推荐与硬性约束校验 | FR-601 ~ FR-606 |
| 一日美食路线与时间表 | FR-701 ~ FR-708 |
| 推荐与信息纠错反馈 | FR-801 ~ FR-804 |

### 4.2 MVP 期望范围（P1）

| 能力 | 对应需求 |
|------|----------|
| 未登录浏览 | FR-105 |
| 地点对比、区域框选探索、偏好加权展示、区域热度展示 | FR-210 ~ FR-213 |
| 情境化临时偏好、记忆冲突处理 | FR-309、FR-310 |
| 内容去重聚合、摘要、来源适配层、用户提交内容 | FR-405 ~ FR-408 |
| 任务重跑、协作关系可视 | FR-511、FR-512 |
| 候选数量控制、宝藏小店倾向、排序依据可见 | FR-607 ~ FR-609 |
| 行程草稿多版本、行程导出 | FR-709、FR-710 |
| 主动询问节制、纠错状态回显 | FR-805、FR-806 |

注意：可访问性相关能力（含减少动态效果设置，NFR-307）属于 P0 非功能要求，不在本节的可降级范围内。

画像 B（本地小店探索者）的成功标志依赖 FR-211 与 FR-608 两项 P1 能力。若二者均降级交付，MVP 对画像 B 的价值验证不成立，需在开发日志中记录该风险。

### 4.3 MVP 之外（P2 及不做）

| 项目 | 处置 |
|------|------|
| 多平台内容全量自动同步 | P2 |
| 实时排队时长预测 | P2 |
| 多人协作编辑行程 | P2 |
| 社区动态、关注、点赞、评论 | 不做（项目计划书 5.2 列为暂不包含范围） |
| 订座、支付、商户后台 | 不做 |
| 无授权自动化抓取内容 | 永久禁止，属合规红线 |
| 医疗或营养诊断 | 永久禁止 |
| 拟人化 Agent 角色与 3D 场景 | P2（项目计划书 9.2 列为可暂缓，非永久禁止） |

### 4.4 范围变更约束

新增需求必须同时满足：与美食发现、信息整理、推荐、旅行规划四类目标之一直接相关；不引入新的合规风险；能在验收标准中写出可判定条件。否则记入本文档第十一章未决问题，不进入实现。

## 五、术语表

术语表是跨文档、代码命名和 Agent 结构化输出的统一词汇来源。实现代码中的模型名、字段名和 Agent 输出字段应与本表英文名保持一致。

| 中文术语 | 英文名 | 定义 |
|----------|--------|------|
| 地点 | place | 餐厅、小吃摊、市场等可到达的美食消费点，是推荐与行程的最小空间单位 |
| 地点来源 | place source | 某条地点信息的出处记录，含来源类型、更新时间、可信度 |
| 内容条目 | content item | 来自授权内容来源的一条公开内容，含标题、链接、摘要、发布时间 |
| 需求约束 | constraint | 用户表达的可判定条件，分硬性约束与软性偏好 |
| 硬性约束 | hard constraint | 违反即淘汰候选的条件，如忌口、预算上限、时间窗、区域 |
| 软性偏好 | soft preference | 影响排序但不淘汰候选的条件，如偏好小店、偏好清淡 |
| 评价 | review | 地点的公开评价及其摘要、标签与情感倾向 |
| 收藏 | favorite | 用户对某地点的收藏记录，含个人备注与“已去过”标记 |
| 反馈 | feedback | 用户对地点、推荐或行程提交的评价性或纠错性输入 |
| 记忆条目 | memory item | 一条持久化的用户偏好，含类型、值、来源、置信度、更新时间 |
| 明示记忆 | stated memory | 用户直接表达并确认的偏好，可用于硬性约束 |
| 推测记忆 | inferred memory | 系统据行为推断的偏好，仅可用于排序，不可当作事实 |
| 推荐结果 | recommendation | 一次推荐请求产生的候选集合及其排序、理由、来源 |
| 推荐理由 | rationale | 说明候选与用户需求、偏好匹配关系的可读说明 |
| 行程 | trip | 一次美食旅行计划，包含若干天与若干时段 |
| 行程节点 | trip item | 行程中的单个安排，含地点、时段、预计到达、停留时长、锁定状态 |
| 锁定节点 | locked item | 用户标记为不允许 Agent 自动修改的行程节点 |
| Agent 任务 | agent task | 一次 Agent 执行单元，含状态、输入摘要、输出摘要、错误信息 |
| 会话 | session | 一次连续的用户需求表达与推荐交互过程 |
| 时效提示 | freshness notice | 对信息更新时间与过期风险的显式提示 |
| 降级结果 | degraded result | 在依赖不可用时给出的、已标注局限的可用结果 |

## 六、功能需求

需求描述格式：编号、标题、优先级、需求陈述、约束与边界。可验证条件统一在 [`验收标准.md`](验收标准.md) 中定义。

### 6.1 账户与个人设置（FR-1xx）

| 编号 | 标题 | 优先级 | 需求陈述 |
|------|------|--------|----------|
| FR-101 | 账户注册与登录 | P0 | 用户可通过 Supabase Auth 完成注册与登录，登录状态在应用重启后保持有效 |
| FR-102 | 登出与本地数据清理 | P0 | 用户登出后，本地缓存的私有数据（记忆、行程、收藏）不可被下一个登录用户读取 |
| FR-103 | 基础个人设置 | P0 | 用户可设置默认城市、默认人均预算区间、默认交通方式、忌口清单 |
| FR-104 | 隐私说明与数据删除入口 | P0 | 设置页提供隐私说明，并提供“删除全部偏好记忆”与“删除账户数据”入口，删除操作需二次确认 |
| FR-105 | 未登录浏览 | P1 | 未登录用户可浏览地图与地点详情，但不可使用推荐、记忆、行程能力，触发时引导登录 |

约束与边界：

- 账户体系仅服务于数据归属与隔离，不做社交关系。
- FR-104 的删除必须真实删除服务端记录，不允许仅隐藏。
- 未登录态不得写入任何 `memory item`。

### 6.2 地图与地点探索（FR-2xx）

| 编号 | 标题 | 优先级 | 需求陈述 |
|------|------|--------|----------|
| FR-201 | 地图基础展示 | P0 | 地图页展示当前视野内的美食地点标记，支持缩放、平移、定位到当前位置 |
| FR-202 | 标记聚合 | P0 | 地点密集时以聚合点展示，避免标记重叠导致不可点选 |
| FR-203 | 关键词搜索 | P0 | 用户可按名称、菜系、菜品关键词搜索地点，结果同时在地图与列表中呈现 |
| FR-204 | 结构化筛选 | P0 | 支持按菜系、价格区间、距离、评分、营业状态、特色标签筛选，筛选条件可组合、可清除 |
| FR-205 | 列表视图 | P0 | 地图结果必须提供等价的列表或卡片视图，不以地图标记作为唯一信息通道 |
| FR-206 | 地点详情 | P0 | 详情页展示名称、类型、地址、营业时间、价格区间、特色菜品、评价摘要、内容提及、信息更新时间 |
| FR-207 | 收藏与去过标记 | P0 | 用户可收藏地点、标记“已去过”、标记“明确喜欢/不喜欢”，并添加个人备注 |
| FR-208 | 加入行程 | P0 | 详情页可将地点加入指定行程的指定日期与时段 |
| FR-209 | 信息更新时间标注 | P0 | 地点的营业时间、价格等易变字段必须显示最近更新时间 |
| FR-210 | 地点对比 | P1 | 用户可选择 2 至 4 个地点进行并列对比，对比维度含价格、距离、评分、特色、排队风险 |
| FR-211 | 区域框选探索 | P1 | 用户可在地图上框选区域，并让 Agent 仅针对该区域执行探索 |
| FR-212 | 偏好加权展示 | P1 | 在用户已有记忆的前提下，地图与列表可按偏好匹配度排序，并标明该排序受偏好影响 |
| FR-213 | 区域热度展示 | P1 | 地图可按区域展示美食密度或热度分布，帮助用户判断值得前往的街区；热度口径与数据来源需在界面说明 |

约束与边界：

- 地点数据通过领域服务访问，UI 不直接调用第三方地图 API（`CLAUDE.md` 技术选型约束第 3 条）。
- 搜索与筛选必须能在无网络时基于缓存给出降级结果，并标注为缓存数据。
- FR-209 缺少更新时间时，显示“更新时间未知”，不得省略该提示。

### 6.3 用户画像与长期记忆（FR-3xx）

| 编号 | 标题 | 优先级 | 需求陈述 |
|------|------|--------|----------|
| FR-301 | 记忆条目结构 | P0 | 每条记忆包含类型、值、来源（明示/推测）、置信度、更新时间、关联证据 |
| FR-302 | 明示偏好录入 | P0 | 用户在设置页或对话中明确表达的偏好，保存为明示记忆 |
| FR-303 | 推测偏好生成 | P0 | 系统可依据搜索、收藏、去过、反馈行为生成推测记忆，并标记为“系统推测” |
| FR-304 | 记忆可见 | P0 | 个人偏好页完整列出系统当前保存的全部记忆，按类型分组，展示来源与更新时间 |
| FR-305 | 记忆可改可删 | P0 | 用户可编辑任意记忆的值、将推测记忆确认为明示记忆、删除单条记忆、清空全部记忆 |
| FR-306 | 写入告知 | P0 | 系统写入或更新记忆时，必须让用户可感知，并提供撤销入口 |
| FR-307 | 推测记忆使用边界 | P0 | 推测记忆只能影响排序，不能作为硬性约束淘汰候选，也不得在推荐理由中表述为用户已确认的事实 |
| FR-308 | 忌口的强约束地位 | P0 | 忌口类记忆一律视为硬性约束，违反忌口的候选必须淘汰，不得以排序降权替代 |
| FR-309 | 情境化临时偏好 | P1 | 单次会话内表达的临时偏好（如“今天想吃清淡的”）只作用于当前会话，默认不写入长期记忆；跨会话反复出现的城市或场景维度偏好（如“在成都偏好本地小店”）可经用户确认后保存为带情境范围的记忆条目，并仅在该情境下生效 |
| FR-310 | 记忆冲突处理 | P1 | 新信息与既有记忆冲突时，明示记忆优先于推测记忆；两条明示记忆冲突时向用户确认，不静默覆盖 |

约束与边界：

- 记忆遵循“用户可见、用户可控、最小化保存”原则，不保存与推荐无关的行为数据。
- 记忆属于用户私有数据，必须由 RLS 与服务端权限双重隔离（见 NFR-501）。
- 未经用户确认，不得把单次否定反馈升级为长期记忆。

### 6.4 多来源信息整合（FR-4xx）

| 编号 | 标题 | 优先级 | 需求陈述 |
|------|------|--------|----------|
| FR-401 | 来源标注 | P0 | 每条外部信息展示来源类型与可跳转出处（若来源允许跳转） |
| FR-402 | 信息分层标注 | P0 | 信息必须区分三层：可验证事实、创作者主观体验、Agent 推断，界面上可分辨 |
| FR-403 | 时效提示 | P0 | 超过设定时效阈值的信息标注“可能已过期”，并降低其在推荐依据中的权重 |
| FR-404 | 不确定性提示 | P0 | 缺乏交叉验证、疑似推广、来源单一的信息必须显式提示，不得呈现为确定结论 |
| FR-405 | 去重与聚合 | P1 | 指向同一地点的多条内容需去重合并，保留信息量最大的条目并保留全部出处 |
| FR-406 | 内容摘要 | P1 | 对长内容生成摘要，摘要不得引入原文不存在的事实 |
| FR-407 | 来源适配层 | P1 | 内容来源以可替换适配器接入，单一来源不可用时其余能力不受影响 |
| FR-408 | 用户提交内容 | P1 | 用户可提交笔记、照片、体验反馈，作为独立来源类型参与展示 |

约束与边界：

- 仅接入公开许可或授权来源；禁止无授权自动化抓取（`CLAUDE.md` 技术选型约束第 2 条，属合规红线）。
- 摘要与推断必须可追溯到具体来源条目，无法追溯的结论不得展示。
- 用户上传内容需做类型、大小、内容校验（见 NFR-505）。

### 6.5 Agent 编排与工作室（FR-5xx）

Agent 职责划分沿用项目计划书第 6.4 节的八类职责。MVP 阶段允许合并实现，但对用户暴露的任务状态必须覆盖“理解需求、检索候选、研究内容、读取偏好、核验信息、排序推荐、生成路线、汇总结果”八个阶段，与项目计划书第 6.4 节的八类职责一一对应。其中“研究内容”阶段承载 FR-4xx 的来源整理与标注产出；内容来源不可用时该阶段状态为“跳过”并说明原因，不得从工作室中省略。

| 编号 | 标题 | 优先级 | 需求陈述 |
|------|------|--------|----------|
| FR-501 | 自然语言需求解析 | P0 | 系统将用户自然语言输入解析为结构化需求，含区域、时间窗、人数、预算、菜系、忌口、交通方式、其他约束 |
| FR-502 | 解析结果确认 | P0 | 解析结果以可读形式回显给用户，用户可逐项修改后再执行 |
| FR-503 | 缺失信息追问 | P0 | 关键约束缺失时，Agent 最多集中追问一轮，其余字段使用默认值并标明默认来源 |
| FR-504 | 任务状态可见 | P0 | Agent 工作室展示上述八个阶段各任务的职责说明、状态（等待、执行中、完成、失败、跳过）与阶段性输出摘要 |
| FR-505 | 输入输出摘要 | P0 | 每个任务展示关键输入与输出摘要及其来源，不暴露不必要的内部思维链 |
| FR-506 | 超时与重试 | P0 | Agent 调用设置超时与重试上限，超限后返回明确失败原因与可用的降级结果 |
| FR-507 | 失败降级 | P0 | 单个任务失败时，其余任务的可用产出仍需汇总呈现，并标注结果不完整 |
| FR-508 | 中断与取消 | P0 | 用户可随时取消进行中的推荐或规划，取消后不产生记忆写入与行程变更 |
| FR-509 | 工具最小权限 | P0 | Agent 工具权限遵循最小权限原则；写入记忆、修改行程等高影响操作需用户确认或提供撤销 |
| FR-510 | 成本上限 | P0 | 单次会话的模型调用次数与 token 消耗设上限，触顶时停止并告知用户 |
| FR-511 | 任务重跑 | P1 | 用户可在修改约束后仅重跑受影响的任务，而非重跑全流程 |
| FR-512 | 协作关系可视 | P1 | 工作室展示任务间的依赖关系与数据流向 |

约束与边界：

- Agent 编排运行于 Supabase Edge Functions，客户端不得直接持有 LLM 或地图服务密钥（`CLAUDE.md` 技术栈规范）。
- 结构化输出必须符合 `packages/contracts/` 中定义的契约，契约不匹配按任务失败处理。
- 不得为提升可解释性而输出无依据的推理过程；理由必须来自实际使用的输入。

## 八、数据与隐私要求

### 8.1 数据分类

| 类别 | 示例 | 存储与访问要求 |
|------|------|----------------|
| 公开数据 | 地点基础信息、公开内容摘要 | 可缓存，可跨用户共享 |
| 用户私有数据 | 记忆、收藏、行程、反馈、上传内容 | RLS 隔离 + 服务端校验，仅本人可读写 |
| 敏感凭据 | 服务端密钥、地图密钥、LLM 密钥 | 仅服务端持有，禁止进入客户端包与日志 |
| 派生数据 | 推测记忆、推荐排序结果、内容摘要 | 需标注来源与生成方式，可被用户删除 |

### 8.2 隐私要求

1. 首次使用需说明将记录哪些偏好、用途与关闭方式。
2. 位置权限按需申请，说明用途，拒绝后提供手动选择城市的替代路径。
3. 用户可导出或删除自身数据；删除为真实删除。
4. 派生数据随源数据删除而失效，不得在源数据删除后继续影响推荐。

## 九、Agent 行为规范

以下规范约束 Agent 对用户可见的行为，属于需求而非实现建议，违反视为缺陷。

| 编号 | 规范 |
|------|------|
| AB-01 | 不虚构地点、菜品、价格、营业时间与内容出处 |
| AB-02 | 无法确认的事实必须标注为不确定，不得用流畅表述掩盖缺失依据 |
| AB-03 | 不把推测记忆表述为用户已确认的偏好 |
| AB-04 | 不静默放宽用户的硬性约束；需放宽时先说明冲突并征求同意 |
| AB-05 | 不静默写入或修改长期记忆与行程 |
| AB-06 | 失败时说明失败环节与影响范围，不以模糊措辞掩盖 |
| AB-07 | 不输出与美食旅行无关的建议，明确拒绝医疗、营养诊断类请求 |
| AB-08 | 追问集中且必要，避免多轮零散提问消耗用户耐心 |
| AB-09 | 推荐理由只引用本次实际使用的输入与来源 |
| AB-10 | 涉及排队、供应、季节性等易变信息时，同时给出信息时间与替代方案 |

## 十、依赖与假设

### 10.1 外部依赖

| 依赖 | 用途 | 不可用时的影响 | 应对 |
|------|------|----------------|------|
| 地图与地理编码服务 | 地图展示、地点检索、距离计算 | 地图能力受限 | NFR-203 降级到列表与缓存 |
| 路线与通行时间服务 | 行程通行时间估算 | 时间估算精度下降 | 使用直线距离估算并标注为粗略估计 |
| LLM 服务 | 需求解析、摘要、排序解释 | 推荐与解析不可用 | 保留搜索、筛选、手动行程编辑 |
| 授权内容来源 | 探店信息与地方攻略 | 信息维度减少 | NFR-204 标注信息不完整 |
| Supabase 平台 | 数据、认证、存储、实时、函数 | 核心能力不可用 | 展示明确错误并保留本地缓存查看 |

### 10.2 假设

1. 目标地区可获得合规的地图与地点数据授权。
2. 至少一个内容来源可通过授权接口或公开许可方式接入；若全部不可得，FR-4xx 降级为仅展示地图数据与用户提交内容。
3. 用户愿意在获得可解释推荐的前提下让系统记录美食偏好。
4. MVP 面向单人使用场景，不需要协作编辑。
