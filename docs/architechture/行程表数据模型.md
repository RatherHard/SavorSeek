# 行程表数据模型

## 1. 文档目的

本文定义 SavorSeek 行程计划在 Supabase PostgreSQL 中的**数据结构与完整性约束**，作为后续数据库迁移、领域模型及 Flutter 行程页面实现的共同依据。

本文中的“行程表”指由以下三张业务表共同组成的行程计划聚合，而不是一张包含全部信息的宽表：

- `trips`：行程计划，是聚合根和权限边界。
- `trip_days`：行程中的自然日。
- `trip_items`：某一自然日内按顺序安排的地点到访或休息项。

此外，`trip_idempotency_keys` 是与行程写入 RPC 配套的幂等辅助表，不属于行程业务聚合实体，但同样受用户级隐私策略保护。

本文仅约束行程计划的核心持久化结构。路线分段、冲突检测结果、Agent 任务、变更历史、推荐依据和分享能力不在本版本范围内。

## 2. 建模原则

1. **行程计划是唯一聚合根**：所有行程日和行程项必须归属于一个 `trip`。
2. **精确时间优先**：计划起止时间是权威数据；“午餐”“下午茶”等时段仅作语义标签。
3. **核心字段显式化**：日期、时间、地点、顺序、预算、状态和锁定信息必须使用明确字段，不得把整个行程保存为不可校验的 JSONB。
4. **派生数据不作为事实源**：路线距离、交通耗时、冲突数量和预算合计应由现有数据计算，不直接保存在 `trips` 中。
5. **地点引用与快照并存**：行程项引用当前地点数据，同时保留规划时快照，避免地点被合并、下架或更新后历史行程不可读。
6. **用户可接管**：地点、时间和顺序分别锁定，Agent 不得修改被锁定的字段。
7. **单用户私有**：MVP 不支持多人共同编辑；一个行程只属于一个已认证用户。
8. **单时区、单币种**：一个行程只使用一个 IANA 时区和一个 ISO 4217 币种。

## 3. 通用数据约定

### 3.1 标识与时间

- 主键统一使用 UUID，默认由数据库生成。
- `created_at`、`updated_at` 使用 `timestamptz`，由数据库维护，统一以 UTC 存储。
- 行程边界使用本地日期 `date`；行程项使用绝对时间 `timestamptz`。
- 将行程项归入哪一天时，必须按 `trips.timezone` 转换为当地日期，不得按客户端设备时区或 UTC 日期判断。
- 时区必须使用 IANA 标识，例如 `Asia/Shanghai`，不得只保存 `UTC+8` 一类固定偏移。

### 3.2 金额

- 金额统一以最小货币单位的整数保存，例如人民币 150.00 元保存为 `15000` 分。
- 金额字段使用 `bigint`，不得使用 `float`、`double precision` 等浮点类型。
- 同一行程的预算与行程项估价统一继承 `trips.currency_code`。
- `trips.budget_limit_minor` 与 `trip_days.budget_limit_minor` 按 `budget_scope` 解释；当日预算继承父行程的 `budget_scope`。
- `trip_items.estimated_cost_min_minor` 与 `estimated_cost_max_minor` 始终表示**整个同行组的预计总额**，不得按人均口径写入。

### 3.3 坐标

- 地点快照中的经纬度必须同时存在或同时为空。
- 坐标系必须显式记录，MVP 允许值为 `gcj02` 或 `wgs84`；禁止在未转换的情况下混用坐标系。
- 高德供应商特有的路线 ID、错误码和原始响应不得进入本模型。

### 3.4 枚举

数据库中的枚举值使用小写 `snake_case`。客户端和 Edge Function 必须通过共享契约映射，不得依赖界面文案作为状态值。

## 4. `trips`：行程计划表

### 4.1 职责

`trips` 表示一个由用户拥有的完整美食旅行计划，是以下能力的边界：

- 身份授权与 RLS；
- 行程总体日期、人数、预算和交通偏好；
- 行程生命周期；
- 乐观并发控制；
- 下属行程日和行程项的级联生命周期。

### 4.2 字段定义

| 字段 | PostgreSQL 类型 | 可空 | 默认值 | 约束与语义 |
|------|-----------------|------|--------|------------|
| `id` | `uuid` | 否 | `gen_random_uuid()` | 主键，创建后不可修改 |
| `user_id` | `uuid` | 否 | 无 | 外键指向 `auth.users(id)`；只能取当前认证用户 ID |
| `title` | `varchar(80)` | 否 | 无 | 去除首尾空白后长度为 1～80 个字符 |
| `timezone` | `text` | 否 | `'Asia/Shanghai'` | 有效 IANA 时区 |
| `start_date` | `date` | 否 | 无 | 行程时区下的开始日期 |
| `end_date` | `date` | 否 | 无 | 不得早于 `start_date` |
| `party_size` | `smallint` | 否 | `1` | 取值范围 1～50 |
| `currency_code` | `char(3)` | 否 | `'CNY'` | 大写 ISO 4217 货币代码 |
| `budget_limit_minor` | `bigint` | 是 | `null` | 总预算或人均预算上限；非负整数 |
| `budget_scope` | `text` | 是 | `null` | `per_person` 或 `total`；必须与预算上限同时为空或同时有值 |
| `default_travel_mode` | `text` | 否 | `'walking'` | `walking`、`cycling`、`transit`、`driving` |
| `status` | `text` | 否 | `'draft'` | 见 8.1 节生命周期状态机 |
| `revision` | `bigint` | 否 | `1` | 正整数；每个成功的行程聚合写事务递增一次 |
| `archived_at` | `timestamptz` | 是 | `null` | 归档时间；归档与业务状态相互独立 |
| `created_at` | `timestamptz` | 否 | `now()` | 由数据库生成 |
| `updated_at` | `timestamptz` | 否 | `now()` | 任一聚合内容变化后由数据库更新 |

### 4.3 数据库检查约束

至少实现以下检查：

```text
end_date >= start_date
party_size BETWEEN 1 AND 50
budget_limit_minor IS NULL OR budget_limit_minor >= 0
(budget_limit_minor IS NULL AND budget_scope IS NULL)
OR
(budget_limit_minor IS NOT NULL AND budget_scope IN ('per_person', 'total'))
currency_code ~ '^[A-Z]{3}$'
revision >= 1
```

`timezone` 由数据库触发器校验，必须存在于 PostgreSQL 的 `pg_timezone_names` 中；服务端契约层也应在进入写入函数前执行同等校验。行程创建后，任何直接或受控写入都不得修改 `trips.timezone`；当前版本已移除时区迁移 RPC。

### 4.4 禁止保存的字段

`trips` 不得保存以下派生值或其他领域状态：

- `is_generating`、`agent_status`：属于 Agent 任务；
- `has_conflict`、`conflict_count`：属于冲突检测结果；
- `total_cost`：应由有效行程项估价汇总；
- `total_distance`、`total_duration`、完整路线几何：属于路线计算结果；
- 用户长期偏好或记忆内容；
- 多人协作者列表、公开分享令牌、支付或订座状态。

## 5. `trip_days`：行程日表

### 5.1 职责

`trip_days` 表示行程时区下的一个自然日，用于组织当日行程项，并承载当日可用时间窗口。即使 MVP 首先只生成一日路线，也必须显式建模行程日，避免后续多日行程通过重复字段拼接。

### 5.2 字段定义

| 字段 | PostgreSQL 类型 | 可空 | 默认值 | 约束与语义 |
|------|-----------------|------|--------|------------|
| `id` | `uuid` | 否 | `gen_random_uuid()` | 主键 |
| `trip_id` | `uuid` | 否 | 无 | 外键指向 `trips(id)`，删除行程时级联删除 |
| `local_date` | `date` | 否 | 无 | 按行程时区解释的自然日 |
| `available_start_time` | `time` | 是 | `null` | 用户当天可用时间窗口的开始时间 |
| `available_end_time` | `time` | 是 | `null` | 用户当天可用时间窗口的结束时间 |
| `budget_limit_minor` | `bigint` | 是 | `null` | 当日预算上限；继承 `trips.budget_scope`，为空时使用行程总预算约束 |
| `notes` | `varchar(1000)` | 是 | `null` | 用户可见备注；空字符串应规范化为 `null` |
| `created_at` | `timestamptz` | 否 | `now()` | 由数据库生成 |
| `updated_at` | `timestamptz` | 否 | `now()` | 由数据库维护 |

### 5.3 唯一性与检查约束

- `UNIQUE (trip_id, local_date)`：同一行程内一个自然日只能有一条记录。
- 为支持 `trip_items` 的复合外键，必须额外保证 `UNIQUE (id, trip_id)`。
- `available_start_time` 与 `available_end_time` 必须同时为空或同时有值。
- 两者有值时，`available_end_time` 必须晚于 `available_start_time`。
- `budget_limit_minor` 必须为空或大于等于 0。
- `local_date` 必须位于父行程的 `[start_date, end_date]` 范围内。该跨表不变量必须由事务函数、触发器或领域服务保证，不能只依赖普通 `CHECK`。
- 修改 `trips.start_date` 或 `trips.end_date` 时，若现有 `trip_days.local_date` 将超出新范围，整个写事务必须失败，不得静默删除行程日。

## 6. `trip_items`：行程项表

### 6.1 职责

`trip_items` 表示时间表中的最小可编辑活动。MVP 支持两类：

- `place_visit`：到访餐厅、小店或其他美食地点；新建时必须同时提供 `place_id` 与合规快照，地点被删除后外键可置空但快照保留。
- `break`：不关联地点的休息时间。

候选地点不得以“未排期行程项”的形式混入本表；候选应保留在推荐结果或 Agent 提案中。

### 6.2 字段定义

| 字段 | PostgreSQL 类型 | 可空 | 默认值 | 约束与语义 |
|------|-----------------|------|--------|------------|
| `id` | `uuid` | 否 | `gen_random_uuid()` | 主键 |
| `trip_id` | `uuid` | 否 | 无 | 冗余保存所属行程，用于 RLS 与复合完整性校验 |
| `trip_day_id` | `uuid` | 否 | 无 | 与 `trip_id` 组成复合外键，必须指向同一行程的 `trip_days` |
| `item_type` | `text` | 否 | 无 | `place_visit` 或 `break` |
| `place_id` | `uuid` | 是 | `null` | 当前地点引用；新建 `place_visit` 时必填，地点后续删除或合并时可置空，但必须保留快照 |
| `title` | `varchar(120)` | 否 | 无 | 用户可见标题，去除首尾空白后长度为 1～120 个字符 |
| `planned_start_at` | `timestamptz` | 否 | 无 | 预计开始时间 |
| `planned_end_at` | `timestamptz` | 否 | 无 | 预计结束时间，必须晚于开始时间 |
| `time_slot` | `text` | 否 | `'flexible'` | 语义时段，见 6.3 节；不替代精确时间 |
| `position` | `integer` | 否 | 无 | 当日展示与路线顺序，从 0 开始的非负整数 |
| `estimated_cost_min_minor` | `bigint` | 是 | `null` | 整个同行组的预计最低费用，非负整数 |
| `estimated_cost_max_minor` | `bigint` | 是 | `null` | 整个同行组的预计最高费用；同时存在时不得低于最低费用 |
| `notes` | `varchar(1000)` | 是 | `null` | 用户可见备注；空字符串规范化为 `null` |
| `status` | `text` | 否 | `'planned'` | `planned`、`completed`、`skipped` |
| `is_place_locked` | `boolean` | 否 | `false` | 为真时 Agent 不得替换地点或改变地点快照 |
| `is_time_locked` | `boolean` | 否 | `false` | 为真时 Agent 不得修改起止时间或语义时段 |
| `is_order_locked` | `boolean` | 否 | `false` | 为真时 Agent 不得改变所在日期和 `position` |
| `created_by` | `text` | 否 | `'user'` | `user`、`agent` 或 `system` |
| `source_agent_task_id` | `uuid` | 是 | `null` | 可追溯到生成该项的 Agent 任务；删除任务不得级联删除行程项 |
| `place_snapshot` | `jsonb` | 是 | `null` | 地点规划时快照；`place_visit` 必填，结构见 6.4 节 |
| `created_at` | `timestamptz` | 否 | `now()` | 由数据库生成 |
| `updated_at` | `timestamptz` | 否 | `now()` | 由数据库维护 |

### 6.3 `time_slot` 允许值

```text
breakfast
morning
lunch
afternoon_tea
dinner
late_night
flexible
```

时段值用于分组和表达用户意图。营业时间校验、冲突判断与路线计算必须使用 `planned_start_at` 和 `planned_end_at`。

### 6.4 `place_snapshot` 结构约束

`place_snapshot` 是版本化 JSON 对象，最小结构如下：

```json
{
  "schema_version": 1,
  "name": "地点名称",
  "address": "规划时的地址摘要",
  "latitude": 39.9042,
  "longitude": 116.4074,
  "coordinate_system": "gcj02",
  "verified_at": "2026-08-21T10:00:00Z"
}
```

约束如下：

- `schema_version` 必须为正整数；当前版本固定为 `1`。
- `name` 必须为非空字符串。
- `latitude` 和 `longitude` 必须同时存在或同时为空。
- `latitude` 范围为 `[-90, 90]`，`longitude` 范围为 `[-180, 180]`。
- 坐标存在时，`coordinate_system` 必须为 `gcj02` 或 `wgs84`。
- `verified_at` 表示地点信息最近一次核验时间；未知时可以为 `null`，不得伪造当前时间。
- 快照只用于历史可读性和解释，不替代 `places` 表中的当前权威数据。
- 外部来源的任意原始响应、鉴权信息和未使用字段不得写入快照。

数据库至少检查 `place_snapshot` 为 JSON 对象；完整字段结构由共享 JSON Schema、Edge Function 输入校验和契约测试共同保证。

### 6.5 关联与检查约束

至少实现以下约束：

```text
FOREIGN KEY (trip_day_id, trip_id)
  REFERENCES trip_days (id, trip_id)
  ON DELETE CASCADE

planned_end_at > planned_start_at
position >= 0
estimated_cost_min_minor IS NULL OR estimated_cost_min_minor >= 0
estimated_cost_max_minor IS NULL OR estimated_cost_max_minor >= 0
estimated_cost_min_minor IS NULL
  OR estimated_cost_max_minor IS NULL
  OR estimated_cost_max_minor >= estimated_cost_min_minor
```

类型相关约束：

- `item_type = 'place_visit'` 时，`place_snapshot` 必须非空；`place_id` 从结构上允许为空，以保留地点删除或合并后的历史行程。
- 新建或替换 `place_visit` 时，`place_id` 必须非空。该规则必须由受控写入函数或触发器校验，不能实现为永久要求 `place_id IS NOT NULL` 的普通 `CHECK`。
- `item_type = 'break'` 时，`place_id` 必须为空；`place_snapshot` 应为空。
- `place_id` 被公共地点数据删除或合并时允许置空；历史到访项仍通过 `place_snapshot` 保持可读。

时间与顺序约束：

- 有效行程项在同一行程日内的 `position` 必须唯一。当前迁移使用 `(trip_day_id, position)` 的无条件唯一索引；节点状态不再包含 `cancelled`，因此不需要部分索引。
- `planned_start_at` 按 `trips.timezone` 转换后的本地日期必须等于 `trip_days.local_date`。
- 允许行程项跨越午夜，因此 `planned_end_at` 的本地日期可以晚于 `trip_days.local_date`。
- 行程项时间重叠、营业时间冲突、交通时间不足或预算超限属于规划可行性问题，不应一律由数据库拒绝；系统必须生成结构化提示，并由用户决定是否调整。

## 7. 聚合级不变量

以下规则涉及多张表，必须在受控的服务端事务中校验：

1. `trip_days` 和 `trip_items` 的最终所有者必须与 `trips.user_id` 一致。
2. 不得通过构造 UUID 把其他用户的行程日、行程项、地点私有备注或 Agent 任务关联到当前行程。
3. 新增、修改、移动或删除任一 `trip_day` / `trip_item` 时，父行程的 `revision` 必须且只能递增一次。
4. 写命令必须携带 `expected_revision`；它与当前 `trips.revision` 不一致时，服务端必须拒绝覆盖并返回可恢复的并发冲突。
5. 可重试的写命令必须携带幂等键，避免网络重试导致重复行程项。
6. Agent 不得修改任何对应锁定标志为真的字段；所有行程聚合写入必须通过受控服务端事务完成。
7. 行程创建后不得修改 `trips.timezone`；当前版本已移除时区修改 RPC，数据库触发器会拒绝任何行程时区变更。
8. 当前数据库触发器在修改币种时检查 `trip_days.budget_limit_minor` 与行程项估价；若这些子级金额存在则拒绝修改 `trips.currency_code`。`trips.budget_limit_minor` 本身不在该触发器的 `money_exists` 查询中，因此只有行程级预算而无子级金额时，特权写入仍可能改币种；客户端没有直接 DML 权限，且当前没有修改币种 RPC。若未来开放币种修改，必须先补齐这一数据库不变量或在受控事务中显式换算/清空全部金额。
9. 行程删除时，`trip_days`、`trip_items` 级联删除；地点或 Agent 任务删除不得级联删除行程业务数据。
10. 用户账户删除时，其私有行程数据必须按隐私策略删除，不得用无限期软删除替代用户数据删除。

## 8. 状态约束

### 8.1 行程状态

`trips.status` 允许值：

- `draft`：草稿，可编辑；
- `confirmed`：用户已确认计划；
- `in_progress`：行程正在执行；
- `completed`：行程已结束；
- `cancelled`：行程已取消。

合法转换：

```text
draft -> confirmed
confirmed -> in_progress
in_progress -> completed
draft -> completed
confirmed -> completed
draft -> cancelled
confirmed -> cancelled
in_progress -> cancelled
```

约束：

- 不得仅根据系统时间自动改变业务状态；“即将开始”或“已过期”属于派生展示状态。
- `completed` 和 `cancelled` 不得恢复为活动状态；如需复用，应复制为新的 `draft` 行程并生成新 UUID。
- 当前版本允许 `draft -> completed` 与 `confirmed -> completed` 的直接完成路径；这是为了支持行程页的显式完成操作，不要求先经过 `in_progress`。
- 归档使用 `archived_at`，不得额外增加 `archived` 业务状态。

### 8.2 行程项状态

`trip_items.status` 允许值：

- `planned`：计划执行；
- `completed`：已完成；不可再编辑或删除。
- `skipped`：用户跳过；不可再编辑或删除。

合法转换：

```text
planned -> completed
planned -> skipped
```

`completed` 和 `skipped` 是行程项终态。若用户希望重新安排，应创建新的 `planned` 行程项，不得重用终态记录伪装成新计划。

## 9. RLS 与写入边界

- `trips`、`trip_days`、`trip_items` 的读取权限均须验证父行程满足 `trips.user_id = auth.uid()`。
- 插入 `trips` 时，`user_id` 必须由服务端取 `auth.uid()`；创建后不得修改所有者。
- 认证客户端不得直接 `INSERT`、`UPDATE` 或 `DELETE` 三张基础表；所有写入必须通过数据库 RPC 或 Edge Function 的受控事务执行。
- 受控事务必须校验所有权、`expected_revision`、幂等键、状态转换、锁定字段及跨表不变量，并在成功后只递增一次父行程修订号。
- RLS 只负责用户数据隔离，不能替代状态机和聚合完整性校验。
- Edge Function 即使使用服务角色绕过 RLS，也必须从已验证 JWT 获取用户身份，不得信任请求体中的 `user_id`。

## 10. 索引约束

建议至少建立以下索引：

```text
trips (user_id, updated_at DESC)
trips (user_id, status, start_date)
trip_days UNIQUE (trip_id, local_date)
trip_days UNIQUE (id, trip_id)
trip_items (trip_id, trip_day_id, planned_start_at)
trip_items (place_id) WHERE place_id IS NOT NULL
trip_items UNIQUE (trip_day_id, position)
```

索引名称应遵循项目统一命名规则；数据库迁移中必须验证查询计划，避免仅为“可能使用”而预建大量索引。

## 11. 明确不在本版本建模的内容

以下内容后续应使用独立表或契约，不得提前塞入三张核心表：

- 相邻行程项之间的路线分段和路线几何；
- 营业时间冲突、路线过长、预算超限、排队风险等检测结果；
- Agent 任务状态、Agent 虚拟角色和协作过程；
- Agent 变更提案、撤销记录和审计日志；
- 推荐理由、内容来源和证据引用；
- 多人协作、公开分享与权限角色；
- 订座、支付、订单和履约状态；
- 酒店、航班、景点等泛旅行实体。

## 12. 已落地实现与后续确认事项

以下内容已由迁移链实现并在自建实例核对，不再是编写初始迁移前的待确认项：

1. `trip_items.place_id` 关联 `places(id)`，地点删除时 `ON DELETE SET NULL`；历史可读性由 `place_snapshot` 保证。
2. 行程标题上限为 80，行程日与行程项备注上限为 1000；行程项支持硬删除，但已完成/已跳过项由受控写入 RPC 保护，不允许删除或编辑。
3. 节点状态不包含 `cancelled`；如果产品需要表达“暂时不去”，应新增独立的意图/取消记录模型，而不是恢复已删除的节点状态。

以下事项仍需后续产品或架构决策，但不影响当前核心表结构：

1. 路线规划是否使用高德服务；无论选择何种供应商，领域字段仍须保持供应商无关。
2. 地点数据在数据库中的规范坐标系，以及 GCJ-02 与 WGS84 的转换边界。
3. 行程项物理删除的审计与保留期限；当前数据库仅保留已完成/已跳过项不可删除的业务规则。
4. 预算上限是否需要支持现有“总预算”和“人均预算”以外的按日覆盖规则。
