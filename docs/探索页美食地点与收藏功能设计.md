# 探索页美食地点与收藏功能设计

## 1. 文档说明

### 1.1 文档目的

本文定义 SavorSeek 探索页（`P-MAP`）中美食地点的展示、查看、收藏及其与行程的衔接方式，作为后续产品原型、Flutter 页面实现、Supabase 数据迁移、接口契约和测试用例的共同依据。

本文重点解决以下问题：

- 用户如何在地图上发现一批美食地点；
- 用户如何在地图和列表之间切换并找到具体地点；
- 用户如何查看地点详情、判断信息是否可靠和及时；
- 用户如何收藏或取消收藏地点，并在网络异常时得到可恢复反馈；
- 地点收藏如何与登录、我的页、长期偏好和行程功能衔接。

本文是功能设计文档，不代表其中所有能力已经完成。文中明确区分当前已实现、部分实现、已设计和待实现内容。

### 1.2 当前基线

截至 2026-08-27，仓库中已经能够核对的基础能力如下：

| 能力 | 当前状态 | 依据 |
|------|----------|------|

## 2. 产品目标与边界

### 2.1 产品目标

探索页不是传统“商户列表”，而是以地图为主工作区、以地点卡片为决策辅助的美食发现入口。用户应能完成：

1. 输入关键词或选择探索条件；
2. 在地图上理解地点的空间分布；
3. 用列表快速浏览、筛选和排序候选；
4. 打开地点详情，查看基本事实、信息更新时间和可执行操作；
5. 收藏值得以后考虑的地点；
6. 将地点加入已有行程；
7. 返回“我的”页管理收藏，并继续影响后续推荐。

### 2.2 MVP 范围

本设计建议按以下优先级实施：

**MVP 必须实现**

- 关键词检索结果在地图上显示；
- 地图与地点列表双向联动；
- 点击标记或地点卡片打开详情；
- 详情显示名称、类别、地址、坐标可用性和信息更新时间；
- 详情提供收藏/取消收藏、加入行程；
- 收藏操作要求认证，未登录时给出登录引导；
- 收藏写入具备幂等、重复点击保护和失败恢复；
- 收藏结果能够在“我的”页读取；
- 空结果、无坐标、网络失败、未认证、服务端错误均有明确状态。

**后续实现**

- 按菜系、价格、距离、评分、营业状态和标签筛选；
- “搜索当前视野”和定位周边检索；
- 地点对比；
- 地图框选区域并交给 Agent 探索；
- 地点评价、内容平台摘要、用户笔记和“已去过”；
- 基于收藏行为更新长期偏好；
- 推荐地点的理由、来源与不确定性卡片。

**明确不做**

- 客户端直接持有高德 Web 服务 Key；
- 未获授权的内容平台自动化抓取；
- 在收藏表中复制完整高德原始响应；
- 以收藏替代订座、支付或订单履约；
- 仅靠地图标记传递地点事实；
- 用动画或 Agent 角色表情替代收藏状态、来源和错误文本。

## 3. 信息架构

### 3.1 页面结构

```text
P-MAP 探索
├── 顶部状态区
│   ├── 当前城市/定位状态
│   ├── 搜索入口或指令栏上下文
│   └── 筛选入口（MVP 可先留为扩展位）
├── 地图主工作区
│   ├── 地点标记
│   ├── 聚合点（地点数量较多时）
│   ├── 当前选中标记
│   └── 地图版权与合规信息
├── 地点结果列表入口
│   └── 可展开的底部结果抽屉/结果卡片
├── 地点详情面板
│   ├── 基本信息
│   ├── 信息时效与来源提示
│   └── 收藏、加入行程等操作
└── 底部 Agent 指令栏
```

地图是主要展示内容，底部 Agent 指令栏继续固定显示，不因结果列表或详情面板出现而永久遮挡地图。详情面板建议采用底部 Sheet；当用户从列表进入时，Sheet 和列表应共享同一地点选择状态，而不是各自维护一份地点对象。

### 3.2 地图与列表双视图

地图标记适合表达空间关系，不适合承载全部文字和状态。因此必须提供列表或卡片视图，满足以下场景：

- 用户无法准确点击重叠标记；
- 地点缺少坐标，无法落点；
- 辅助技术无法使用地图画布；
- 用户需要连续比较多个地点；
- 地图加载失败但地点结果仍然可读。

建议交互：

- 默认显示地图；检索成功后在地图下方提供“查看 N 个地点”入口；
- 上拉打开结果抽屉，抽屉内显示地点卡片；
- 点击地点卡片：地图相机移动到地点（有坐标时）并打开详情；
- 点击地图标记：选中对应卡片并打开详情；
- 点击地图空白处：清除当前选中状态并关闭详情；
- 结果抽屉打开时，地图仍保留可见区域，避免用户失去空间上下文；
- 若地点数量超过单屏可读范围，列表使用懒加载或分段加载，不一次性创建大量复杂 Widget。

### 3.3 地点卡片

地点卡片是地图之外的主要可访问入口。MVP 卡片应包含：

| 信息 | 要求 |
|------|------|
| 名称 | 必填，最多两行，超长省略但可在详情完整查看 |
| 主类别 | 从高德类别串取最具体的末级类别，如“烧烤” |
| 地址 | 有值时展示；缺失时不渲染空占位行 |
| 距离 | 仅在有可靠参考点和距离计算能力时展示，不伪造 |
| 收藏状态 | 已收藏/未收藏必须有图标和文本语义 |
| 信息时效 | 可显示“更新于 X”；列表可用较弱视觉层级 |
| 操作入口 | 收藏、查看详情；加入行程放在详情内避免卡片过载 |

卡片的收藏按钮只负责收藏，不应同时触发卡片选择或打开详情。点击区域需有明确语义和足够触控面积。

## 4. 地图表现与状态

### 4.1 标记规则

地点标记由探索页根据领域模型构造，`AmapSurface` 只负责接收并渲染标记，不读取 Repository 或收藏状态。

建议标记状态：

| 状态 | 表现 | 事实来源 |
|------|------|----------|
| 普通地点 | 默认地点标记 | 地点结果 |
| 已收藏 | 收藏标识或颜色辅助 | 当前用户收藏状态 |
| 当前选中 | 放大/高亮并显示名称 | 当前 UI 选择状态 |
| 多地点聚合 | 数字聚合点 | 当前视野内标记数量 |
| 无坐标地点 | 不落地图，保留在列表 | `Place.hasCoordinates == false` |
| 信息较旧 | 不用颜色单独断言失效，在卡片显示更新时间 | `fetchedAt` |

颜色不是唯一状态通道。收藏、选中、风险和数据时效必须同时提供图标、文本或辅助技术语义。地图 SDK 若无法稳定支持自定义收藏图标，列表和详情仍必须准确表达收藏状态。

### 4.2 视野与结果生命周期

- 新检索开始时，清除旧地点选中项，显示加载状态；
- 旧请求晚于新请求返回时，必须丢弃旧响应，不能覆盖新结果；
- 新结果到达后，只有存在坐标的地点构造标记；
- 标记集合应缓存，避免每次 Widget rebuild 都被插件判定为全量删除和新增；
- 结果失败时保留地图底图，并在地图上显示可读的状态提示；
- 检索空结果与服务失败分开表达；
- 地图未配置、用户未同意隐私政策或地图 SDK 不可用时，结果列表和错误说明不能消失；
- 进入后台或页面不可见时暂停非必要的动画，不能影响地点数据和收藏状态。

### 4.3 聚合策略

聚合属于后续增强能力，MVP 可以先使用高德插件已有能力或仅展示有限数量标记。真正实施时应满足：

- 聚合点显示数量；
- 点击聚合点放大地图或展开该区域列表；
- 聚合不能吞掉无坐标地点；
- 聚合点不能成为唯一信息入口；
- 地图缩放或结果变化后，聚合状态必须与当前标记集合一致；
- 聚合算法不改变地点 ID、顺序和收藏事实。

## 5. 地点查看设计

### 5.1 打开详情的入口

以下入口应打开同一套 `PlaceDetailSheet` 或等价详情组件：

1. 点击地图标记；
2. 点击列表卡片；
3. 从推荐结果卡片进入；
4. 从收藏列表进入。

详情组件不应自行查询地图 SDK 或直接写数据库。它接收地点、收藏状态和操作回调，由容器层负责数据协调。

### 5.2 详情内容层级

**第一层：立即决策信息**

- 地点名称；
- 主类别；
- 地址；
- 收藏状态与收藏按钮；
- “加入行程”按钮；
- 关闭按钮。

**第二层：可信度与时效**

- 信息更新时间，如“信息更新于 3 小时前”；
- 数据来源，如“地点基础信息来自高德”；
- 缺失字段提示，如“暂未取得坐标”；
- 对营业、价格、排队等易变事实的谨慎说明。

当前 `Place` 模型已具备名称、类别、地址、经纬度和 `fetchedAt`，因此第一阶段不要在 UI 中虚构评分、价格、营业状态或菜品。等后端模型提供对应字段并具备来源后再展示。

**第三层：扩展信息**

后续可增加：

- 特色菜品；
- 评价摘要；
- 授权内容来源；
- 用户笔记；
- 推荐理由；
- 去过状态；
- 与其他地点的对比。

每一项扩展信息都必须标注来源、更新时间或“不确定性”，并区分事实、他人主观体验和 Agent 推断。

### 5.3 详情操作

| 操作 | 未登录 | 已登录 | 失败后行为 |
|------|--------|--------|------------|
| 收藏 | 打开登录引导或显示登录后可收藏 | 创建收藏 | 保留未收藏状态，显示可重试提示 |
| 取消收藏 | 不应出现已收藏状态 | 删除收藏 | 恢复已收藏状态，允许重试 |
| 加入行程 | 按现有实现显示登录/行程引导 | 打开排期表单 | 不清除详情，便于继续操作 |
| 关闭 | 直接关闭 | 直接关闭 | 不受网络影响 |
| 查看来源 | 后续扩展 | 后续扩展 | 来源不可用时显示缺失而非伪造 |

收藏与加入行程是两个独立动作。收藏表达“以后想保留”，加入行程表达“安排到具体时间”，不能因为加入行程自动收藏，也不能因为取消收藏从行程中删除地点。

## 6. 收藏功能设计

### 6.1 收藏语义

收藏是用户私有的轻量地点标记，表示用户希望稍后查看、比较或纳入规划。收藏不等同于：

- 已去过；
- 喜欢或不喜欢；
- 对地点事实的认可；
- 对营业状态、价格或推荐结果的确认；
- 对 Agent 修改长期记忆的授权。

MVP 只做收藏/取消收藏和收藏列表，不在收藏表中混入评价、打分、访问记录或长期偏好推断。

### 6.2 数据模型建议

当前数据库已有公共 `places` 表，但没有 `favorites` 表。建议新增迁移，例如：

```sql
create table public.favorites (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id) on delete cascade,
  place_id uuid not null references public.places(id) on delete cascade,
  note varchar(500),
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  constraint favorites_user_place_uq unique (user_id, place_id),
  constraint favorites_note_ck check (
    note is null or char_length(btrim(note)) between 1 and 500
  )
);

create index favorites_user_created_idx
  on public.favorites (user_id, created_at desc);
```

设计说明：

- `user_id + place_id` 唯一，保证重复点击和请求重试不会产生重复收藏；
- `on delete cascade` 只删除用户收藏关系，不改变公共地点或其他用户收藏；
- 地点被公共数据清理时，收藏关系可以随地点删除；若未来需要保留历史收藏，应改为软失效或保存最小快照，并另行决策；
- `note` 本阶段可暂不开放 UI，但预留长度受限字段，避免后续无约束扩展；
- 不保存完整高德原始响应、用户 JWT、设备信息或未经授权的外部内容。

### 6.3 RLS 与写入方式

收藏属于用户私有数据，必须启用 RLS：

```sql
alter table public.favorites enable row level security;

create policy favorites_select_own on public.favorites
  for select to authenticated
  using (user_id = auth.uid());

create policy favorites_insert_own on public.favorites
  for insert to authenticated
  with check (user_id = auth.uid());

create policy favorites_update_own on public.favorites
  for update to authenticated
  using (user_id = auth.uid())
  with check (user_id = auth.uid());

create policy favorites_delete_own on public.favorites
  for delete to authenticated
  using (user_id = auth.uid());
```

如果项目继续沿用行程表“表只读、写入走 `security definer` RPC”的严格模式，则收藏也应统一通过受控 RPC 写入，而不是给客户端开放 DML。推荐接口：

```text
add_favorite(p_place_id uuid, p_idempotency_key uuid)
remove_favorite(p_place_id uuid, p_idempotency_key uuid)
list_favorites(p_limit integer, p_offset integer)
```

RPC 必须：

- 使用 `auth.uid()` 作为用户身份，不能接受客户端传入的 `p_user_id`；
- 校验地点存在且属于公共地点表；
- 对重复添加返回已有收藏或幂等成功，而不是唯一键异常；
- 对重复删除返回幂等成功，或返回明确的“本来就未收藏”结果；
- 限制分页上限，避免无界查询；
- 不向客户端暴露数据库堆栈、服务端密钥或完整原始响应；
- 写入函数设置安全的 `search_path`，并撤销不必要的公开执行权限。

最终采用“RLS 直接 DML”还是“security definer RPC”应在实现收藏迁移前确认，并与现有 Supabase 权限策略保持一致，不应两套模式并存而没有理由。

### 6.4 Flutter 领域接口

建议在 `apps/mobile/lib/features/places/` 下新增收藏相关接口，保持 UI 不依赖 Supabase 具体实现：

```dart
abstract interface class FavoriteRepository {
  Future<Set<String>> loadFavoritePlaceIds();

  Future<void> addFavorite({
    required String placeId,
    required String idempotencyKey,
  });

  Future<void> removeFavorite({
    required String placeId,
    required String idempotencyKey,
  });
}
```

可根据分页收藏列表再增加：

```dart
abstract interface class FavoriteListRepository {
  Future<List<FavoritePlace>> listFavorites({
    int limit = 20,
    int offset = 0,
  });
}
```

建议的容器层状态至少包含：

- 当前地点收藏 ID 集合；
- 正在写入的地点 ID 集合；
- 最近一次失败的地点 ID、错误类型和可重试性；
- 收藏列表的载入、空、成功、失败状态。

收藏状态属于用户维度，不能放入公共 `Place` 事实模型中。可以在 UI ViewModel 中派生 `isFavorite(place.id)`，避免把同一地点对象复制成多个带用户状态的事实副本。

### 6.5 乐观更新与并发

收藏是低风险、可撤销的用户动作，可采用乐观更新，但必须可回滚：

1. 用户点击未收藏按钮；
2. 立即把地点标记为“已收藏”，按钮进入写入中；
3. 生成并保存本次操作的幂等键；
4. 调用收藏 Repository；
5. 成功后清除写入中状态；
6. 失败后恢复原状态，显示具体错误和“重试”；
7. 同一地点写入期间禁用重复点击；
8. 收藏与取消收藏的连续操作使用操作序号，旧响应不能覆盖较新的意图。

如果用户在请求未完成时再次点击，建议先禁用该地点按钮，而不是立即排队反向操作。后续如需要支持快速撤销，应为每个地点建立显式操作队列并测试顺序一致性。

网络重试必须复用同一 `idempotencyKey`。重新发起一次全新的业务动作才生成新键，不能在同一次请求的超时重试中生成多个键。

### 6.6 未登录行为

未登录用户可以浏览已公开且已授权显示的地点结果，但不能检索需要认证的服务端地点接口，也不能收藏。当前 `places-search` 已在客户端和 Edge Function 两侧要求认证。

收藏按钮的建议行为：

- 图标仍可见，表示该功能存在；
- `onPressed` 打开登录/注册面板，而不是无反馈禁用；
- 辅助技术标签说明“登录后收藏”；
- 用户取消登录后回到原详情，不显示失败提示；
- 登录成功后不自动重复执行刚才的收藏，除非用户再次确认，避免未经明确意图写入。

## 7. 容器层与数据流

### 7.1 推荐数据流

```text
用户输入关键词
      ↓
ExplorePage / SearchController
      ↓
PlaceRepository.searchByKeywords
      ↓
places-search Edge Function
      ↓
places 公共地点结果
      ↓
探索页容器状态
   ┌──┴──────────────┐
   ↓                 ↓
地图标记          地点列表
   └──────┬─────────┘
          ↓ 选择地点
     PlaceDetailSheet
       ┌──┴─────────┐
       ↓            ↓
  收藏状态       加入行程
       ↓            ↓
FavoriteRepository  PlaceScheduler
       ↓            ↓
 favorites 私有表  trips / trip_items
```

### 7.2 单一事实源

- `places` 是公共地点基础事实的来源；
- `favorites` 是用户与地点之间收藏关系的来源；
- `PlaceSearchController` 管理检索请求、结果和当前选中地点；
- 收藏 Controller/Notifier 管理当前用户收藏状态和写入状态；
- 地图标记和卡片是状态投影，不是独立数据存储；
- 行程中的 `place_snapshot` 是规划时历史快照，不能被收藏状态反向修改；
- Realtime（未来如接入）只做通知，数据库仍是收藏事实来源。

### 7.3 依赖注入

`AppDependencies` 后续增加：

```dart
final FavoriteRepository favoriteRepository;
```

未配置后端时注入 `UnavailableFavoriteRepository`，其错误应明确表示“收藏服务尚未就绪”，而不是返回空集合。测试和离线演示可注入内存 Fake，但不得在生产页面中放置模拟收藏数据。

ExplorePage 建议只依赖抽象接口：

```dart
ExplorePage(
  placeRepository: dependencies.placeRepository,
  favoriteRepository: dependencies.favoriteRepository,
  scheduler: dependencies.scheduler,
)
```

## 8. 状态、空态与错误处理

### 8.1 检索状态

沿用当前地点检索状态机，并补充列表投影：

| 状态 | 地图 | 列表/提示 | 可执行动作 |
|------|------|-----------|------------|
| 空闲 | 显示底图 | 显示输入引导 | 输入关键词 |
| 加载中 | 保留底图，显示加载浮标 | 暂不替换旧列表或按产品选择清空 | 等待 |
| 成功有结果 | 显示有坐标标记 | 显示地点卡片数量 | 查看、收藏、加入行程 |
| 成功无结果 | 保留底图 | “没有找到相符地点” | 修改关键词、扩大范围 |
| 网络失败 | 保留底图 | 明确网络错误 | 重试 |
| 未认证 | 保留底图 | 登录后才能检索/收藏 | 登录 |
| 配置错误 | 保留底图或地图降级 | 联系管理员，不给无意义重试 | 返回/稍后再试 |
| 上游不可用 | 保留底图 | 服务暂时不可用 | 重试或查看已有结果 |

### 8.2 收藏状态

每个地点的收藏状态建议为：

```text
notFavorite
  ↓ 点击
saving
  ├─ 成功 → favorite
  └─ 失败 → notFavorite + 可重试错误
favorite
  ↓ 点击
removing
  ├─ 成功 → notFavorite
  └─ 失败 → favorite + 可重试错误
```

不能使用单个全局 `isLoading` 锁住所有地点。用户收藏 A 时，B 的收藏按钮仍应可用；只有同一个地点的按钮需要防重复提交。

### 8.3 典型错误文案

错误文案面向用户，业务分支使用稳定的错误类型或错误码：

| 场景 | 建议文案 | 是否重试 |
|------|----------|----------|
| 未登录 | “登录后即可收藏地点。” | 否，转登录 |
| 网络中断 | “无法保存收藏，请检查网络后重试。” | 是 |
| 会话过期 | “登录状态已失效，请重新登录。” | 否，转登录 |
| 地点不存在 | “这个地点已无法收藏，可能已被下架。” | 否 |
| 唯一键冲突 | 按幂等成功处理 | 否 |
| 服务端暂时不可用 | “收藏服务暂时不可用，请稍后重试。” | 是 |
| 权限错误 | “当前账号无法修改这条收藏。” | 通常否，记录日志 |

不要把 PostgreSQL 错误码、堆栈、请求 URL 或服务密钥显示给用户。

## 9. 可访问性与交互质量

### 9.1 地图替代入口

- 地点标记不能作为唯一信息入口；
- 必须有语义化地点列表；
- 地图加载失败时，地点列表仍可读；
- 详情面板使用明确标题和可访问关闭按钮；
- 卡片和按钮提供语义化 `Semantics` 标签；
- 收藏按钮标签应随状态变化，例如“收藏 老长春烧烤”“取消收藏 老长春烧烤”；
- 加载和错误状态通过语义播报或可聚焦文本呈现，不只显示转圈或颜色；
- 触控目标尽量不小于 44×44 logical pixels；
- 文字不依赖地图背景对比度，详情和卡片使用稳定表面色；
- 颜色、图标、文字三者至少保留两种状态线索；
- 遵守系统减少动态效果设置，地图动画和列表过渡不应影响操作。

### 9.2 键盘与辅助技术

虽然主要目标是移动端，Flutter Widget 仍应支持：

- 键盘焦点在搜索框、结果卡片、收藏按钮和关闭按钮之间按合理顺序移动；
- 按 Enter/Space 可触发聚焦控件；
- 当前选中地点有可读焦点或高亮状态；
- 列表滚动后焦点不跳到已销毁的卡片；
- 错误提示不会因焦点丢失而无法找到；
- 地图手势不应阻断外层可访问列表的操作。

## 10. 安全、隐私与合规

1. 收藏是用户私有数据，所有查询和写入必须以认证用户为边界；
2. 不能接受客户端传入的 `user_id` 作为权限依据；
3. 地点公共数据与收藏私有数据分表存储；
4. 高德 Web 服务 Key 只存 Edge Function 环境变量，不能进入 Flutter 包、日志或错误文案；
5. 收藏备注如开放，必须限制长度并做输入校验；
6. 地点名称、地址和外部内容在 UI 中按普通文本渲染，不把未经清洗的内容当作 HTML；
7. 外部来源链接后续开放时，只允许白名单协议和必要主机，不能直接导航到任意用户输入 URL；
8. 不在日志中记录完整 JWT、收藏备注、用户邮箱或未脱敏外部响应；
9. 数据删除策略需覆盖账户删除时的 `favorites` 级联清理；
10. 收藏行为是否进入长期记忆必须单独获得产品与隐私决策，不能默认把一次收藏解释为稳定口味偏好；
11. 地图版权标识、隐私同意信息和必要归属不能被详情面板、像素覆盖层或列表遮挡；
12. 当前开发环境仍使用 HTTP Supabase 地址，收藏上线前应优先完成 HTTPS，明文传输不得用于公开发布。

## 11. 埋点与可观测性

埋点只记录实现产品分析所需的最小信息，不记录敏感内容。建议事件：

| 事件 | 关键属性 | 用途 |
|------|----------|------|
| `explore_search_submitted` | 查询类型、城市、结果请求 ID | 分析检索入口 |
| `place_results_loaded` | 结果数量、是否缓存、耗时区间 | 监控检索体验 |
| `place_selected` | place ID、入口（marker/list） | 分析地点查看 |
| `place_detail_viewed` | place ID、来源入口 | 分析详情使用 |
| `favorite_add_started` | place ID、入口 | 观察收藏意图 |
| `favorite_add_succeeded` | place ID、耗时区间 | 观察成功率 |
| `favorite_add_failed` | 错误类别、是否可重试 | 定位故障 |
| `favorite_remove_succeeded` | place ID、入口 | 分析取消行为 |
| `place_added_to_trip` | place ID、trip ID 是否存在 | 衡量闭环 |

不应记录：完整关键词原文、完整地址、用户笔记、JWT、服务端密钥、完整高德原始响应。若产品确实需要分析查询词，应先完成隐私评估、脱敏和保留期限设计。

服务端应记录可检索的请求 ID、错误类别、耗时、上游状态和数据库操作结果；错误日志不得把用户可见文案当作唯一诊断依据。

## 12. 测试与验收标准

### 12.1 单元测试

至少覆盖：

- `Place.primaryCategory` 的空值、空串和分层类别；
- `Place.fromJson` 对 numeric/String 经纬度的解析；
- 无坐标地点不会生成地图标记；
- 新检索结果会清除旧选中项；
- 旧请求响应不会覆盖新请求；
- 收藏状态转换：未收藏 → 保存中 → 已收藏；
- 保存失败后回滚为未收藏；
- 已收藏 → 删除中 → 未收藏；
- 删除失败后回滚为已收藏；
- 同一地点写入中禁止重复提交；
- 重试复用同一个幂等键；
- 未登录收藏进入登录引导；
- 收藏列表空态与加载失败状态。

### 12.2 Widget 测试

至少覆盖：

- 地点列表显示名称、类别、地址和更新时间；
- 点击列表卡片打开详情；
- 点击标记选择正确地点；
- 点击地图空白处关闭详情；
- 收藏按钮根据状态显示正确图标、文案和 Semantics；
- 收藏写入中按钮禁用且显示进度；
- 收藏失败显示可操作错误，不丢失原收藏状态；
- 未登录时显示登录后收藏说明；
- 无坐标地点仍出现在列表；
- 地图不可用时列表或状态内容仍可用；
- 空结果、网络失败和配置错误的提示各不相同；
- 不同屏幕尺寸下底部指令栏、列表和详情没有横向溢出。

### 12.3 集成与安全测试

- 登录用户只能读取自己的收藏；
- 用户 A 不能读取、修改或删除用户 B 的收藏；
- 未认证请求不能调用收藏写入接口；
- 重放同一幂等键不会创建重复收藏；
- 并发添加同一地点不会产生两行；
- 重复取消不会导致错误状态或异常堆栈下发；
- 地点删除后的外键行为符合最终决策；
- 账户删除会清理收藏数据；
- RLS、函数权限和 `search_path` 经过数据库审查；
- 错误响应不包含 JWT、内部 SQL、API Key 或完整上游响应。

### 12.4 端到端关键流程

```text
登录
  → 探索页输入“烧烤”
  → 地图和列表显示地点
  → 打开“老长春烧烤”详情
  → 收藏
  → 关闭详情并重新打开，仍显示已收藏
  → 进入“我的”查看收藏列表
  → 取消收藏
  → 返回探索页，状态同步为未收藏
  → 再将地点加入已有行程
```

### 12.5 验收标准

| 编号 | 验收标准 |
|------|----------|
| EXP-001 | 用户可通过关键词获得地点结果，地图和列表显示同一批地点 |
| EXP-002 | 点击地图标记或列表卡片都能打开对应地点详情 |
| EXP-003 | 无坐标地点不会产生错误地图标记，但仍出现在列表 |
| EXP-004 | 详情显示名称、类别、地址（若有）和信息更新时间 |
| EXP-005 | 收藏状态在标记、卡片和详情之间保持一致 |
| EXP-006 | 收藏写入重复点击不会产生重复记录 |
| EXP-007 | 收藏失败会回滚视觉状态，并提供明确的可重试动作 |
| EXP-008 | 未登录用户点击收藏能进入登录引导，不出现无反馈控件 |
| EXP-009 | 用户只能看到和修改自己的收藏 |
| EXP-010 | 收藏可以在“我的”页读取和取消 |
| EXP-011 | 收藏不会自动修改行程，也不会未经确认写入长期记忆 |
| EXP-012 | 检索、收藏和地图失败时，页面仍提供可理解的降级状态 |

## 13. 实施顺序与任务拆分

### 阶段一：收藏数据层

1. 确认 `favorites` 删除策略和写入模式；
2. 编写数据库迁移、索引、RLS 或 RPC；
3. 用数据库测试验证跨用户隔离、唯一性和幂等；
4. 在 `packages/contracts` 或当前 Repository 边界确定收藏契约；
5. 实现 `FavoriteRepository`、Supabase 实现、Unavailable 实现和 Fake。

### 阶段二：探索页结果列表

1. 新增地点结果抽屉或列表组件；
2. 抽取地点卡片，统一地图标记、列表和详情的选择状态；
3. 增加无坐标地点列表降级；
4. 保留当前 `PlaceSearchController` 的过期响应保护；
5. 为列表和地图交互补 Widget 测试。

### 阶段三：详情与收藏闭环

1. 扩展 `PlaceDetailSheet` 接收收藏状态和操作回调；
2. 增加收藏状态 Controller/Notifier；
3. 实现乐观更新、回滚、重试和重复点击保护；
4. 加入登录引导和会话变化后的收藏状态重新加载；
5. 让收藏状态投影到卡片与标记，但不修改 `Place` 公共事实模型。

### 阶段四：“我的”页与集成验证

1. 把 `MinePage` 的“收藏的地点”占位分区接入收藏列表；
2. 支持打开详情和取消收藏；
3. 增加端到端“检索 → 查看 → 收藏 → 我的 → 取消收藏”流程；
4. 在真实 Supabase 实例验证迁移、RLS、RPC、幂等和错误映射；
5. 在真机验证地图渲染、标记点击、列表抽屉、详情面板和页面生命周期。

### 阶段五：后续扩展

- 搜索当前视野和定位周边；
- 筛选和排序；
- 收藏备注；
- 地点对比；
- 已去过与用户反馈；
- 由 Agent 生成推荐理由；
- 收藏行为进入长期记忆前的用户可见提案与确认机制。

## 14. 待确认事项

以下事项不应在编码时自行猜测：

1. 收藏表中地点删除后是级联删除、软失效还是保留快照；
2. 收藏写入统一采用 RLS 直接 DML，还是沿用行程的 `security definer RPC` 模式；
3. 收藏备注是否纳入 MVP；
4. 未登录用户是否允许浏览缓存地点结果，还是所有地点检索都必须登录；
5. 列表采用底部抽屉、全屏列表还是地图/列表分栏；
6. 收藏行为是否产生即时埋点、是否进入用户长期记忆；
7. 地点排序是否严格保留高德相关性，还是允许按距离、收藏状态和用户偏好重排；
8. 评分、价格、营业状态和内容摘要的来源、时效与授权边界。

在这些决策完成前，MVP 应优先实现最小收藏关系和地点基础详情，不应预先引入评价、内容聚合或复杂推荐字段。
