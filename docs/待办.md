## 1. 地图可见范围自动显现美食地点标注（P1）——客户端代码已接入，待平台验收

### 现状

- 地点详情和“关键词检索 → 地图标记 → 详情 → 加入行程”的基础闭环已经实现。
- `AmapSurface` 已转发 `onCameraMoveEnd`；`map_viewport.dart` 已按相机中心、zoom 和地图尺寸计算保守视野半径、近似 bbox，并生成归一化 query key。
- `ExplorePage` 已在地图创建/尺寸就绪和相机停止后使用 400ms 去抖调度视野检索；当前实现仍使用服务端 `around` 接口，不把近似 bbox 冒充为精确 visible-region。
- `PlaceSearchController` 已区分关键词与视野结果，使用请求 generation 防止乱序响应覆盖，并保留关键词结果与地图候选的分层语义；视野刷新失败会保留上一批结果，显式重试不会被成功 query key 去重拦截。
- Marker 投影已进行餐饮类别、有效坐标、有效高德评分、视野范围、去重和空间分散处理；无坐标地点仍保留在结果列表。结果抽屉已接入部分结果和加载更多状态。
- 当前仍未完成 Android/iOS 平台视图与真实地图鉴权验收；首次/刷新空结果的完整体验、登录状态变化后的自动补发、用户级限流和真实目标实例对账仍需验证。

### 期望

用户进入已同意且可用的探索地图后，地图应根据当前可见范围自动显现附近美食地点：

1. 地图创建完成后，以初始相机触发一次周边检索。
2. 用户拖动或缩放地图时不逐帧请求；相机停止移动后，经短暂去抖触发一次检索。
3. 视野变化很小时不重复请求；快速连续移动时，旧请求不能覆盖新视野结果。
4. 检索成功后，有坐标地点显示 Marker，无坐标地点保留在结果列表；Marker、列表和详情继续共享同一地点事实。
5. 自动视野结果不应静默覆盖用户刚提交的关键词结果；展示层要能区分“当前视野自动探索”和“用户关键词检索”。
6. 空结果、首次失败和已有结果刷新失败要分别表达；刷新失败时尽量保留上一批仍可用的地点。
7. 自动检索必须继续经 `places-search` 服务端代理，复用 JWT 校验、缓存、错误码和高德 Key 隔离，不能由客户端直调高德 Web API。

### 为何值得做

这是地图从“被动展示一次搜索结果”变成“以空间视野主动探索”的关键一步，也是项目“地图负责呈现真实空间”目标的必要能力。它可以消除用户移动到新区域后仍看到旧地点的问题，并为后续当前视野筛选、定位周边、聚合和 Agent 地图联动提供稳定入口。

### 推荐落地方案

#### 阶段 A：地图事件与视野模型

- 在 `apps/mobile/lib/features/explore/amap_surface.dart` 增加 `onCameraMoveEnd`，只把 `CameraPosition` 转发给上层；保持地图组件不读取地点仓库、不处理业务状态。
- 新增纯 Dart 视野计算模块（建议 `apps/mobile/lib/features/explore/map_viewport.dart`），根据相机中心、zoom 和地图容器尺寸估算覆盖当前屏幕的周边半径。由于当前插件未提供可靠边界 API，不伪造精确矩形边界。
- 半径取覆盖地图四角的保守距离并乘安全系数，随后限制到服务端允许的 `1..50_000` 米范围；无尺寸时使用保守默认值。坐标、zoom、尺寸和半径都必须做有限值及范围校验。
- 对中心坐标、zoom 和半径做固定精度/档位归一化，生成稳定 query key，减少相邻视野造成的缓存碎片。

#### 阶段 B：自动检索状态和请求生命周期

- 复用 `PlaceRepository.searchAround(latitude, longitude, radiusMeters, keywords)`，不新建第二套网络客户端。
- 扩展 `PlaceSearchController` 的查询上下文，至少区分 `keyword` 与 `viewport`，保留 query key、最近成功视野和请求 generation；继续沿用现有乱序响应保护。
- `ExplorePage` 在地图创建后和 `onCameraMoveEnd` 中调度视野检索：相机移动期间不请求，停止后使用约 300–500ms debounce；变化低于阈值或 query key 未变化时跳过。
- 自动请求 loading 时保留上一批地点和 Marker，显示轻量“正在更新附近地点”；成功后替换自动视野结果；首次空结果或失败显示可理解的地图提示，刷新失败不抹掉上一批可用结果。
- 手动关键词检索保持优先级：刚提交关键词时抑制短时间内的自动更新，或将手动结果与自动结果分层管理；禁止自动请求静默替换用户刚查看的关键词结果。
- 自动刷新期间若当前选中地点仍在新结果中，详情保持打开；若不在新结果中，不立即销毁详情，至少允许用户主动关闭并明确其已离开当前视野。

#### 阶段 C：标记投影、数量和分页

- 继续使用 `ExplorePage._resolveMarkers` 的 Marker ID 映射和结果源缓存；以 `Place.id` 去重并保留服务端相关性顺序。
- 第一版只请求 `page=1`（当前每页 20 条），不因地图移动自动翻完 10 页；结果抽屉的“加载更多”另行设计。
- 暂不实现复杂 Marker 聚合。若真机验证显示单视野地点过多或点击冲突，再单独增加聚合任务；聚合不能替代列表和无坐标降级。

#### 阶段 D：配额、安全与运行期验证

- 复用 `places-search` 的服务端缓存和最小字段落库；必要时增加自动视野请求的用户级频率保护，避免快速平移、恢复前台或多设备消耗高德配额。
- 客户端不携带高德 Web Service Key，不开放 `places` 任意写入，不为本需求提前引入 PostGIS。
- 真机验证地图瓦片鉴权、相机停止事件、首次自动检索、拖动/缩放去抖、快速移动竞态、Marker 点击、详情保持、地图错误降级和页面生命周期。

### 验收标准

- 首次地图创建后自动请求当前视野；未同意、未登录、地图未创建或依赖未配置时不发送请求。
- 相机移动过程中不发送请求；停止后去抖只触发一次有效的归一化查询。
- 小幅相机变化和相同 query key 不重复请求；旧响应不能覆盖新视野。
- 成功结果的有坐标地点显现 Marker，无坐标地点仍在列表；点击自动 Marker 可打开现有 `PlaceDetailSheet`。
- 空结果、首次失败、刷新失败和配置/鉴权错误有不同且可操作的提示；刷新失败保留上一批可用结果。
- 关键词检索结果不会被自动视野请求静默替换；选中地点在刷新期间不无故消失。
- 自动请求继续使用服务端 JWT 校验、缓存和 Key 隔离，单次只加载受控数量，不自动翻页。
- `flutter analyze`、`flutter test`、覆盖率检查通过；Android 真机或模拟器完成平台视图验证。

### 依赖与顺序

1. 先完成/确认高德地图真机渲染、Key 鉴权和相机回调可用性。
2. 先写视野计算纯逻辑和 Controller 状态测试，再实现 UI 接线。
3. 接入自动检索后做全量 Flutter 测试、Supabase around 缓存/错误契约验证和真机验证。
4. 通过 Flutter/Dart、通用代码和安全审查后，再将本项从待办移入开发日志的“已完成/待验证”记录。

## 3. 地点复杂筛选与空间检索闭环完善（P1）

### 现状

当前已完成第一阶段基础接线：

- Flutter 已有结构化 `PlaceSearchQuery`，可表达 bbox、菜系、价格等级、最大距离、营业状态和最低评分。
- `MapViewportQuery` 已根据相机中心、zoom 和实际地图尺寸生成 Web Mercator 近似 bbox，同时保留旧的 around 半径字段。
- `places-search` 已能解析 `kind=bounds`、筛选条件、origin 和 limit；服务端已具备受控分区规划、分区结果合并、bbox 二次裁剪、重复 POI 去重和部分失败元数据。
- `Place` 与 `PlaceSearchResult` 已扩展菜系、价格、营业状态、cursor、partial 和 failed tiles 字段；缺失的供应商字段保持未知，不由客户端推断。
- 新增前向迁移已准备扩展地点筛选字段、bounds 缓存类型、公开投影和客户端原表读取权限；迁移尚未在目标 Supabase 实例应用和对账。

以下能力仍属于“代码已接线但尚未完成生产验收”或“已预留但未实现”：

- 高德多页策略目前只执行受控的分区第一页，尚未基于 `count` 或候选不足条件安全请求第二页。
- 分区调用虽已使用 `Promise.allSettled` 处理部分失败，但尚未完成稳定并发上限、总调用预算、限流退避和缓存击穿保护的运行期验证。
- bounds 聚合结果尚未在真实 Supabase 环境完成完整成功缓存写入、部分结果不缓存、TTL 和旧 RPC 兼容验证。
- 高德价格等级和营业状态字段尚未用当前账号的真实餐饮响应确认；无法确认时必须继续返回 unknown，不得把营业时间当作实时营业状态。
- Web Mercator bbox 仍是基于相机和尺寸的近似范围，不是地图插件返回的精确 visible-region；跨日期变更线、高纬度和不同屏幕尺寸仍需真机验证。
- 当前没有完整的 Deno/Edge Function 自动化测试，环境也尚未安装 Deno；服务端分区、合并、失败和敏感字段脱敏缺少可重复测试证据。
- Flutter 尚未提供可见的筛选面板、筛选 chips、加载更多和部分结果重试入口；Agent 自然语言尚未自动转换为结构化筛选条件。

- [ ] 同一地点跨分区或跨页只出现一次；结果顺序不依赖异步完成顺序；超过调用预算时返回明确 partial 元数据。
- [ ] 全部上游失败返回供应商错误；成功但无匹配地点才返回普通空结果；部分成功不会覆盖完整缓存。
- [ ] 菜系、评分、价格和营业筛选只使用已确认字段；未知值不会被当作满足硬性条件；距离不污染公共地点事实。
- [ ] 地图 marker 只使用当前 viewport/bounds 候选，结果抽屉保留关键词语义；筛选变化、地图移动和旧请求不会造成结果串批。
- [ ] Deno/Flutter/SQL 验证完成，业务逻辑覆盖率达到 80% 以上；完成 Android/iOS 真机或模拟器验证后，再将本项移入开发日志。

## 2. 地点详情增强（P2）——来源与字段可信度仍待完善

### 现状

当前 `PlaceDetailSheet` 已实现基础事实详情：名称、主类别、地址（若有）、有效评分、信息抓取时间、收藏和加入行程。地点详情仍是探索页内嵌面板或“我的”页 modal，而不是独立路由；详情不额外请求数据，也不展示未经后端来源支撑的价格、营业状态、图片、评价或内容摘要。

当前代码已补充来源/坐标系字段的可选模型和展示入口：来源未知时不应默认推断为高德，坐标缺失仍需在详情中明确表达。价格等级和营业状态暂按供应商明确字段处理；`biz_ext.cost` 不再被当作价格等级，未确认字段保持未知。

仍未完成：字段级来源与观测时间、坐标不可用提示的完整 UI 契约、价格/营业/菜系的可信展示、真实供应商字段支持矩阵及对应详情/契约测试。图片、评价和内容摘要不在本次范围内。

### 期望

先补齐已有模型可表达的来源与坐标可用性提示；未来扩展详情字段时，新增独立详情数据契约、来源、更新时间和不确定性表达，不把详情组件直接耦合 Supabase 或地图 SDK。

### 为何值得做

避免把地点基础事实、外部内容和 Agent 推断混在一个不可解释的面板中，保证用户能判断信息新鲜度和可执行性。

## 4. 前端 Agent 对接闭环（P1）——基础接线已完成，可靠性与跨工作区联动待实现

### 现状

- Flutter 已通过 `AgentRepository`、`AgentController` 和 `AgentWorkspacePanel` 接入 Supabase Edge Function `agent`，可以提交 `discover_places` 指令、读取会话投影、订阅 `squad_events`、选择/拒绝推荐和取消会话。
- 指令提交已开始携带提交瞬间的地图视野与选中地点上下文；请求 DTO 位于 `apps/mobile/lib/features/agent/agent_context.dart`。
- Agent 任务失败、超时或 partial 状态已有基础“重试任务”入口；行程草案和决策操作已补齐 `expectedRevision` / `idempotencyKey` 的客户端参数边界。
- 像素小人暂不作为本阶段阻塞项，当前使用 Material 图标和角色名称表达队员身份；后续如接入开源素材，必须先确认许可证、来源和发布范围。
- 当前尚不能宣称 Agent 前端完成：事件恢复仍主要依赖收到 Realtime 后全量刷新，地图/行程投影、命令幂等重试、认证切换清理和草案应用的真实 revision 来源尚未形成完整闭环。

### 待办清单

#### A. Realtime、断线恢复与快照一致性

- [ ] 在 `apps/mobile/lib/features/agent/agent_controller.dart` 实现明确的 `snapshot → list_events(afterSequence) → final snapshot` 恢复流程；充分使用 `list_squad_events` 返回的 `events` 与 `nextSequence`，防止漏事件和重复补齐。
- [ ] 处理 Realtime `SUBSCRIBED`、`CHANNEL_ERROR`、`TIMED_OUT`、`CLOSED` 等状态，增加有限次数和退避的重连策略；连接断开时向队长说明任务仍可在服务端继续执行。
- [ ] 对刷新请求做串行化、节流或 generation 防护，避免每个事件都启动并发 `get_session`，也避免旧会话/旧响应覆盖当前工作区。
- [ ] 继续以数据库 projection 为业务事实源；未知事件类型只能触发安全同步，不能因为前端未识别事件而丢弃整个会话。
- [ ] 补充重复事件、乱序事件、sequence gap、重连、补齐分页、刷新失败和旧 session 事件隔离测试。

#### B. 提交与写操作的幂等性

- [ ] 保留同一队长指令的 `clientRequestId`，在响应丢失或网络失败后允许使用原 ID 重试；不能让用户重复输入同一指令就无条件创建多个会话。
- [ ] 为推荐选择/拒绝、决策确认、草案应用和任务重试增加操作级 in-flight 防护，避免重复点击产生多个不同幂等键。
- [ ] 对同一 apply/写操作的重试复用同一个 `idempotencyKey`；区分“新操作”与“原操作重试”，不在每次按钮点击时盲目生成新键。
- [ ] 对 `apply` 决策只在拿到真实目标行程 `revision` 后启用；缺少 revision、草案已过期或 revision 冲突时必须阻止请求并提供刷新/重新确认路径。
- [ ] 核对后端 `retry_task` 的实际语义：当前编排入口可能把任意失败子任务作为根任务重新运行完整编排，需在服务端修正为阶段级重试或在前端隐藏不安全的子任务重试入口；未完成核对前不能宣称“单任务重试”可靠。

#### C. 认证、隐私与生命周期

- [ ] 监听 `AuthService` 登录、退出和账号切换事件；退出或切换账号时清除 Agent 快照、session ID、事件游标和 Realtime channel，避免上一账号的推荐、地点名和决策残留在当前 UI。
- [ ] 为认证切换、迟到网络响应和迟到 Realtime 回调增加测试；动作执行前确认仍属于当前登录账号。
- [ ] 初次提交失败时提供明确的“重试原指令”路径，保留原始文本和 `clientRequestId`，不要把没有 session 的错误态错误地绑定到 `refresh()`。

#### D. Agent 结果与地图/行程工作区联动
