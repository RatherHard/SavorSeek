## 1. 地图可见范围自动显现美食地点标注（P1）

### 现状

- 地点详情和“关键词检索 → 地图标记 → 详情 → 加入行程”的基础闭环已经实现。
- 探索页首次进入时，地图通过高德合规同意闸门后只显示底图；`PlaceSearchController` 处于 idle，地图没有地点标记。
- 用户在底部指令栏提交非空文本后，`ExplorePage._submitCommand` 调用 `searchByKeywords`，并固定以“大连”为城市条件；检索成功后，`_resolveMarkers` 只为有成对经纬度的地点创建 Marker。
- 地图拖动或缩放目前只改变高德相机，不会触发新的地点检索。`PlaceRepository.searchAround` 和 `places-search` 的 `around` 接口已经存在，但探索页没有调用入口。
- `AmapSurface` 当前只转发地图创建、Marker、Polyline、空白点击和手势等能力，没有转发 `AMapWidget.onCameraMoveEnd`。
- 当前地图插件已确认可回传相机中心点和 zoom，但不能在本项目中假设存在稳定的 visible-region/bounding-box API。

### 期望

用户进入已同意且可用的探索地图后，地图应根据当前可见范围自动显现附近美食地点：

1. 地图创建完成后，以初始相机触发一次周边检索。
2. 用户拖动或缩放地图时不逐帧请求；相机停止移动后，经短暂去抖触发一次检索。
3. 视野变化很小时不重复请求；快速连续移动时，旧请求不能覆盖新视野结果。
4. 检索成功后，有坐标地点显示 Marker，无坐标地点保留在结果列表；Marker、列表和详情继续共享同一地点事实。
5. 自动视野结果不应静默覆盖用户刚提交的关键词结果；展示层要能区分“当前视野自动探索”和“用户关键词检索”。
6. 空结果、首次失败和已有结果刷新失败要分别表达；刷新失败时尽量保留上一批仍可用的地点。
7. 自动检索必须继续经 `places-search` 服务端代理，复用 JWT 校验、缓存、错误码和高德 Key 隔离，不能由客户端直调高德 Web API。

### 为何值得做

这是地图从“被动展示一次搜索结果”变成“以空间视野主动探索”的关键一步，也是项目“地图负责呈现真实空间”目标的必要能力。它可以消除用户移动到新区域后仍看到旧地点的问题，并为后续当前视野筛选、定位周边、聚合和 Agent 地图联动提供稳定入口。

### 推荐落地方案

#### 阶段 A：地图事件与视野模型

- 在 `apps/mobile/lib/features/explore/amap_surface.dart` 增加 `onCameraMoveEnd`，只把 `CameraPosition` 转发给上层；保持地图组件不读取地点仓库、不处理业务状态。
- 新增纯 Dart 视野计算模块（建议 `apps/mobile/lib/features/explore/map_viewport.dart`），根据相机中心、zoom 和地图容器尺寸估算覆盖当前屏幕的周边半径。由于当前插件未提供可靠边界 API，不伪造精确矩形边界。
- 半径取覆盖地图四角的保守距离并乘安全系数，随后限制到服务端允许的 `1..50_000` 米范围；无尺寸时使用保守默认值。坐标、zoom、尺寸和半径都必须做有限值及范围校验。
- 对中心坐标、zoom 和半径做固定精度/档位归一化，生成稳定 query key，减少相邻视野造成的缓存碎片。

#### 阶段 B：自动检索状态和请求生命周期

- 复用 `PlaceRepository.searchAround(latitude, longitude, radiusMeters, keywords)`，不新建第二套网络客户端。
- 扩展 `PlaceSearchController` 的查询上下文，至少区分 `keyword` 与 `viewport`，保留 query key、最近成功视野和请求 generation；继续沿用现有乱序响应保护。
- `ExplorePage` 在地图创建后和 `onCameraMoveEnd` 中调度视野检索：相机移动期间不请求，停止后使用约 300–500ms debounce；变化低于阈值或 query key 未变化时跳过。
- 自动请求 loading 时保留上一批地点和 Marker，显示轻量“正在更新附近地点”；成功后替换自动视野结果；首次空结果或失败显示可理解的地图提示，刷新失败不抹掉上一批可用结果。
- 手动关键词检索保持优先级：刚提交关键词时抑制短时间内的自动更新，或将手动结果与自动结果分层管理；禁止自动请求静默替换用户刚查看的关键词结果。
- 自动刷新期间若当前选中地点仍在新结果中，详情保持打开；若不在新结果中，不立即销毁详情，至少允许用户主动关闭并明确其已离开当前视野。

#### 阶段 C：标记投影、数量和分页

- 继续使用 `ExplorePage._resolveMarkers` 的 Marker ID 映射和结果源缓存；以 `Place.id` 去重并保留服务端相关性顺序。
- 第一版只请求 `page=1`（当前每页 20 条），不因地图移动自动翻完 10 页；结果抽屉的“加载更多”另行设计。
- 暂不实现复杂 Marker 聚合。若真机验证显示单视野地点过多或点击冲突，再单独增加聚合任务；聚合不能替代列表和无坐标降级。

#### 阶段 D：配额、安全与运行期验证

- 复用 `places-search` 的服务端缓存和最小字段落库；必要时增加自动视野请求的用户级频率保护，避免快速平移、恢复前台或多设备消耗高德配额。
- 客户端不携带高德 Web Service Key，不开放 `places` 任意写入，不为本需求提前引入 PostGIS。
- 真机验证地图瓦片鉴权、相机停止事件、首次自动检索、拖动/缩放去抖、快速移动竞态、Marker 点击、详情保持、地图错误降级和页面生命周期。

### 验收标准

- 首次地图创建后自动请求当前视野；未同意、未登录、地图未创建或依赖未配置时不发送请求。
- 相机移动过程中不发送请求；停止后去抖只触发一次有效的归一化查询。
- 小幅相机变化和相同 query key 不重复请求；旧响应不能覆盖新视野。
- 成功结果的有坐标地点显现 Marker，无坐标地点仍在列表；点击自动 Marker 可打开现有 `PlaceDetailSheet`。
- 空结果、首次失败、刷新失败和配置/鉴权错误有不同且可操作的提示；刷新失败保留上一批可用结果。
- 关键词检索结果不会被自动视野请求静默替换；选中地点在刷新期间不无故消失。
- 自动请求继续使用服务端 JWT 校验、缓存和 Key 隔离，单次只加载受控数量，不自动翻页。
- `flutter analyze`、`flutter test`、覆盖率检查通过；Android 真机或模拟器完成平台视图验证。

### 依赖与顺序

1. 先完成/确认高德地图真机渲染、Key 鉴权和相机回调可用性。
2. 先写视野计算纯逻辑和 Controller 状态测试，再实现 UI 接线。
3. 接入自动检索后做全量 Flutter 测试、Supabase around 缓存/错误契约验证和真机验证。
4. 通过 Flutter/Dart、通用代码和安全审查后，再将本项从待办移入开发日志的“已完成/待验证”记录。

## 2. 地点详情增强（P2）

### 现状

当前 `PlaceDetailSheet` 已实现基础事实详情：名称、主类别、地址（若有）、信息抓取时间、收藏和加入行程。它是探索页内嵌面板或“我的”页 modal，而不是独立路由；详情不额外请求数据，也不展示未经后端来源支撑的评分、价格、营业状态、图片、评价或内容摘要。

### 期望

先补齐已有模型可表达的来源与坐标可用性提示；未来扩展详情字段时，新增独立详情数据契约、来源、更新时间和不确定性表达，不把详情组件直接耦合 Supabase 或地图 SDK。

### 为何值得做

避免把地点基础事实、外部内容和 Agent 推断混在一个不可解释的面板中，保证用户能判断信息新鲜度和可执行性。
