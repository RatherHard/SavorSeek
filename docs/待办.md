# 待办

集中记录已确认但尚未开工的改进项。每项说明「现状」「期望」与「为何值得做」，避免只留一句结论导致后来者要重新调研。

已完成或已验证的事项不留在本文档，改由 [`开发日志.md`](开发日志.md) 按日期记录。

## 创建行程时不能选择时区

**现状**：创建行程表单（[`create_trip_sheet.dart`](../apps/mobile/lib/features/trip/create_trip_sheet.dart)）只收集标题、日期、人数、预算，时区固定为 `trips.timezone` 的默认值 `Asia/Shanghai`。用户要规划一趟东京行程，只能先创建再到行程页改时区。

**期望**：表单内直接提供时区选择，复用已有的 [`timezone_picker_sheet.dart`](../apps/mobile/lib/features/trip/timezone_picker_sheet.dart)。

**为何值得做**：跨时区行程的展示与改期都已可用，唯独入口处要绕一圈，是这条路径上唯一的断点。

**实现提示**：创建时行程还没有 `trip_days`，因此不受「一旦存在行程日即不得改时区」这一约束（`validate_trip_row`）；`create_trip` 本就接受 `p_timezone` 参数，无需新增迁移。

## 缺少批量操作

**现状**：取消与删除均为单项操作，行程项菜单一次只作用于一个项。调整多项需逐个打开菜单。

**期望**：支持多选后批量取消或删除。

**为何值得做**：一天里排了五六家店、行程有变时要全部取消，逐个操作既繁琐又容易漏。

**实现提示**：现有 RPC 每次调用都会递增一次 `trips.revision`，批量走循环会让第二次调用起就因 `expected_revision` 过期而返回 `P0002`。需要新增接受 id 数组的 RPC，在单个事务内完成并只递增一次修订号——这与「受控事务必须只递增一次父行程修订号」的既有约定一致（[行程表数据模型](architechture/行程表数据模型.md) 第 326 行）。

---

## 没有统一的撤销入口

**现状**：取消可经菜单「恢复」反悔，但需要用户自己回到列表找到那一项；硬删除不可恢复，仅靠二次确认防误操作。

**期望**：写入成功后的提示条上提供「撤销」，至少覆盖取消、改期、加入行程三类可逆操作。

**为何值得做**：误操作后的第一反应是「撤销」，而不是回列表里找刚才那一项再选恢复。

**实现提示**：撤销需要写入前的原值（改期需原 `trip_day_id` 与起止时刻），故 UI 层要在调用前留存快照。硬删除无法纳入——记录已不存在；若要支持，需改为「先软删除、延迟硬删除」，那是另一项设计决策，不宜与本项混做。
